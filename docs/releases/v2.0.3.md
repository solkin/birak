# Birak v2.0.3

Birak now decodes S3 streaming upload bodies before storing them, resumes
interrupted replica downloads, and avoids redundant repair work after peer
restarts. Reads and health probes no longer wait behind the volume commit lock.

## Changes

- PutObject and UploadPart decode supported `aws-chunked` bodies and verify
  chunk signatures, trailing checksums and decoded length before publication.
  Invalid uploads preserve the previous object or part. Unsupported streaming
  variants return an explicit error.
- Filesystem S3 listing no longer truncates its candidate set at 100000 objects.
  Multipart acknowledgements propagate directory-fsync failures, cleanup checks
  the storage fence, and access logs remove presigned URL credentials.
- Peer replay filters states already present locally. Remaining changes are
  enqueued in one transaction per page; repeated reconciliation does not rewrite
  unchanged queue rows. Queued work starts immediately after daemon restart.
- Interrupted replica downloads of at least 1 MiB retain verified progress.
  Transfers checkpoint every 16 MiB and resume with Range/If-Range after a retry
  or restart, with a full checksum check before publication.
- Small and large files have separate repair lanes, so slow APK transfers do
  not occupy the slots used by icons. Unindexable individual names are counted
  and reported without preventing readiness or replication.
- Sweeps run between event-backlog entries, and shutdown stops between names.
  Readers, probes, scratch traversal and reconciliation comparisons spend less
  time holding the shared commit lock.
- CI checks both source and release-binary vulnerabilities. Docker retains the
  symbol tables needed to distinguish linked code from unused dependencies.

## Upgrade from v2.0.2

- Replication remains on protocol 4 and the release toolchain is Go 1.26.9.
  SQLite adds replica partial-download state and repair-lane metadata on startup.
  Stop the node and back up consistent sync/meta directories, including
  `.birak/storage-id`, before upgrading; retain that backup for rollback.
- Upgrade every endpoint accepting S3 uploads. v2.0.2 could acknowledge an
  `aws-chunked` upload while storing its framing instead of its decoded bytes.
  Compare affected existing objects with their original checksums and upload
  the originals again when they differ. Upgrading cannot repair those objects
  automatically.
- `sync.max_concurrent_downloads` applies to each of two lanes per peer: files
  of 8 MiB and more, and everything else. The combined maximum is twice the
  configured value; review channel and disk budgets before rollout.

## Validation and operational limits

The code included in this release passed full macOS race tests, vet, Linux and
Windows builds, and source/Linux-binary vulnerability scans. The tag workflow
requires Linux race/ENOSPC tests, Windows build and four-node Docker fault/TLS
acceptance before publishing images.

ACK still confirms local durable publication before asynchronous replication.
Production throughput, cold storage, external uplink, backup restore and power
loss require validation on the deployment's hardware. Windows builds do not
establish native NTFS durability.

Retained partial downloads expire by age at startup; a permanently unavailable
source can retain staging space and block replacement of its containing
directory until the transfer is discarded or the node restarts. Missing explicit
configuration files still fall back to defaults/environment, malformed numeric
environment overrides can be ignored, and component failures can exit with
code 0. Validate configuration before rollout and monitor process availability
independently of its exit code.

[intermittent peers and resume](../audits/intermittent-peers-and-resume.md).

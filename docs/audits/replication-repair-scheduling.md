# Очередь восстановления: независимые операции и предел параллелизма

Дата: 2026-09-20. Изменения поверх `47ea00d`.

## Воспроизведённые проблемы

1. Repair выполнялся последовательно, независимо от `max_concurrent_downloads`. Открытая медленная HTTP-загрузка останавливала остальные операции очереди, включая удаления и записи, добавленные во время этой загрузки. В тесте при лимите 2 и `batch_limit: 1` шесть независимых файлов и удаление не завершались, пока первая загрузка удерживалась открытой.
2. Polling и repair имели независимые ограничения. При настроенном лимите 2 тест фактически получал три одновременных скачивания: два от polling и ещё одно от repair.

Оба случая сначала воспроизведены без исправлений:
`/tmp/birak-eighth-red.log` — FAIL.

## Изменения

- Для каждого peer одновременно выполняется не более `max_concurrent_downloads` repair-операций. Имена выполняющихся операций хранятся в ограниченном локальном наборе; одно имя не запускается повторно, пока его worker не завершился.
- Освободившийся worker сразу получает следующую готовую операцию. Периодический rescan продолжает работать во время долгих загрузок, поэтому новые записи тоже получают свободные места.
- Выборка из SQLite ограничена числом worker-слотов. Пропуск уже выполняющихся имён оставляет место следующим строкам; размер страницы `/changes` больше не ограничивает параллелизм repair.
- Скачивания polling и repair используют общий, отменяемый через context лимит **на peer**. Другой peer имеет собственный лимит. Метаданные не занимают слот передачи файла.
- Строка остаётся в SQLite до успешного применения. Существующая проверка `revision` защищает новую queued-версию от завершения старой операции. Постоянных отметок захвата задач, миграции SQLite и нового сетевого протокола нет.
- Успешная запись backoff освобождает worker для другого имени. Ошибка чтения/обновления очереди приостанавливает новые попытки до следующего rescan, чтобы немедленно готовая строка не создала цикл без пауз.
- При отмене цикл дожидается своих worker. Уведомления об окончании ограничены числом worker и не требуют работающего получателя во время shutdown.

При `max_concurrent_downloads: 1` работа с файлами этого peer остаётся
последовательной. Если заняты все разрешённые слоты, новые скачивания ожидают
освобождения места. Общая блокировка локальных filesystem commit сохраняется.

## Регрессии

Все тесты используют реальные HTTP-запросы и SQLite; границы длинных передач
контролируются отправкой части body и каналом завершения.

| Проверка | Условие приёмки |
| --- | --- |
| Уже накопленная очередь и записи, добавленные во время загрузки | Пока первый файл ещё скачивается, остальные шесть файлов и удаление завершаются; старое имя не запускается повторно; незавершённые байты не публикуются |
| Polling и repair одного peer | При лимите 2 третий HTTP download ждёт свободного слота; отмена ожидающего repair сохраняет запись; повторный запуск использует освободившийся слот |
| Два peer | Занятый единственный слот одного источника не мешает получить файл от другого |
| Отмена двух активных передач | HTTP-запросы прекращаются, staging очищается, старые файлы и метаданные остаются; после повторного открытия SQLite обе операции завершаются |
| Новая версия того же имени во время старой загрузки | Нет повторного одновременного запуска; другие имена продолжают работу; старое завершение не удаляет новую операцию, итоговые байты соответствуют новой версии |
| Отказ SQLite при Resolve и Defer | Отказы инъецируются триггерами на настоящей БД. Очередь не теряется, быстрых повторов нет; после снятия отказа очередь завершается |

Новые регрессии находятся в `internal/syncer/repair_scheduling_test.go` и входят
в обычный `go test`. Формат метаданных и протокол **3** сохранены.

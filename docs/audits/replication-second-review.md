# Повторное ревью репликации после первого набора исправлений

> Исторический отчёт о состоянии до исправлений. Результаты следующего прохода и актуальный контракт: [исправления R01–R06](replication-followup-fixes.md). Приёмочные тесты перенесены в обычный набор; build tag больше не нужен.

Дата: 2026-09-19. Проверено текущее рабочее дерево поверх `e454e389234d2cd5a8bb859e60d20a6185aeb6d9`, включая все исправления из [предыдущего отчёта](sync-reliability-fixes.md).

**Вердикт: пока нельзя назвать репликацию «надёжной как молоток» или допускать её к production с обещанием сохранности подтверждённых данных.** Прежние воспроизведения закрыты, но обнаружены пять новых групп проблем и отдельно подтверждён пробел в защите от повреждения содержимого. Некоторые проблемы проявляются без конкуренции, рассинхронизации часов, потери питания и большой нагрузки.

В этом проходе добавлены воспроизводящие тесты и отчёт. Рабочая реализация не менялась. Новые приёмочные тесты запускаются явно с `-tags syncrecheck`: они проверяют безопасный исход и сейчас падают. Их отделение от штатного CI не означает, что дефекты допустимы; после исправления эти сценарии должны войти в обычный набор.

## Подтверждённые результаты

| ID | Приоритет / тип | Сценарий | Наблюдаемый результат |
| --- | --- | --- | --- |
| R01 | P1, потеря записи | SFTP открывает `alias → target`; replica заменяет `target`; клиент пишет через открытый handle и успешно закрывает его | Новые байты записаны в inode, который больше не доступен по имени. На диске остаётся `replica!` вместо `CLIENT!!` |
| R02 | P1, откат успешной операции | COPY или MOVE старого по mtime файла поверх более нового destination; HTTP 204; следующий обычный poll | Неизменённый сосед восстанавливает прежний destination. При MOVE исходное имя уже удалено |
| R03 | P1, потеря при crash recovery | SIGKILL между сохранением старого destination в `.birak-bak-*` и публикацией замены | Стартовая очистка уничтожает backup; watcher записывает tombstone и может распространить удаление |
| R04 | P1, подтверждение записи на неверном storage | Привязанный root отодвинут, на его месте пустой каталог без sentinel; WebDAV PUT | Проверка storage уже выдаёт ошибку, но gateway возвращает HTTP 201 и сохраняет данные в подменном каталоге |
| R05 | P2, условная потеря repair | Один peer URL повторяется в конфигурации; два worker держат старый repair; между их завершениями вставлен новый repair того же имени | Старый worker удаляет новую строку: revision после удаления/повторной вставки снова равна 1 |
| R06 | Пробел модели целостности | Инъекция повреждения одного байта с сохранением size/mtime; checksum scan; синхронизация с исправной копией | Scan объявляет повреждённый hash новой версией; при большем hash повреждённые байты затирают исправную реплику |

P1 здесь означает препятствие выпуску с гарантиями сохранности файлов, а не оценку распространённости сценария. R05 требует двух обработчиков одной очереди; текущая конфигурация разрешает точный дубликат peer URL, а `Run` действительно запускает loops для каждого элемента списка. R06 — результат явно выбранной модели импорта файловых изменений, а не доказательство неисправности конкретного диска.

## Почему это происходит

**R01: защищено имя, но не открытый файл.** [`BusyLocked`](../../internal/fileops/fileops.go) проверяет только `filepath.Abs(path)` в map; `OpenWriter` регистрирует тот же строковый путь. SFTP разрешает symlink на обычный видимый файл внутри root. Handle, открытый по `alias`, не блокирует применение новой версии по `target`. Перепроверка store и общий mutex не помогают: проблема в идентичности защищаемого объекта. Тест использует те же `OpenWriter`, `WriteAt` и close, что и SFTP handler; это white-box проверка, а не отдельный сетевой SFTP-сеанс. Варианты исправления: учитывать идентичность inode и все допускаемые aliases либо явно ограничить writable namespace, запретив такие aliases.

**R02: mtime источника COPY/MOVE принимается за возраст новой операции.** [`copyFile`](../../internal/gateway/webdav/handlers.go) сохраняет исходный mtime через `Chtimes`; MOVE сохраняет его вместе с inode. Watcher безусловно заменяет локальную запись этой более старой меткой. Когда сосед присылает предыдущую версию destination с большим mtime, она снова выигрывает. В тесте источник старше на час, обе ноды используют обычные часы, конкурентных изменений нет. Детерминированное разрешение конфликтов работает согласно текущему правилу, но правило не соответствует порядку успешных пользовательских изменений. Исправление требует отдельной версии изменения, сохраняющей причинный порядок, независимо от пользовательского mtime. Простое сравнение локального счётчика `version` разных нод этого не обеспечит.

**R03: backup принят за мусор.** [`stageReplace`](../../internal/gateway/webdav/handlers.go) сначала переименовывает существующий файл, затем вызывает операцию замены. При живом процессе error-path пытается восстановить оригинал; при SIGKILL этот код не выполняется. [`birakd.run`](../../cmd/birakd/main.go) до открытия store вызывает `SweepTempFiles(root, 0)`, который удаляет `.birak-bak-*` как scratch. Проверен один обычный файл, поэтому оговорка о неатомарных операциях над деревом не снимает проблему. Тест убивает настоящий дочерний процесс внутри реального helper и затем вызывает штатные sweep/indexing; это не общий daemon kill в случайный момент. Нужны подготовка замены до изменения старого имени и явное восстановление незавершённых операций. Backup нельзя удалять по одному только префиксу.

**R04: readiness и разрешение записи независимы.** Sentinel проверяется в watcher/syncer и `/readyz`, но [`fileops.Do`/`Publish`](../../internal/fileops/fileops.go), используемые gateway, не проверяют привязку storage. Воспроизведение использует настоящий WebDAV handler, а не прямой `os.WriteFile` вместо gateway. Readiness во внешнем балансировщике может уменьшить окно, но не защищает уже направленные запросы или прямое подключение. Общая проверка допуска должна выполняться перед открытием writable handle и публикацией в том же механизме записи; отказ storage должен возвращаться клиенту.

**R05: revision защищает UPDATE, но не новую жизнь строки.** [`ResolveRepairItem`](../../internal/store/store.go) удаляет по `(peer_id, name, revision)`. После успешного удаления и нового INSERT revision опять получает DEFAULT 1. Порядок «оба worker прочитали rev=1 → A удалил → новый enqueue создал rev=1 → B удалил» стирает новую операцию. Проверка существующих тестов покрывала только enqueue поверх ещё существующей строки, который увеличивает revision. Нужны уникальное поколение задания, не переиспользуемое после DELETE, и устранение дублирования workers для одного peer. Тест store детерминированно выполняет допустимое чередование операций; отдельный тест config подтверждает условие его доступности.

**R06: обнаружение изменения не равно восстановлению целостности.** [`inspectFile`](../../internal/watcher/watcher.go) видит несовпадение hash и записывает новый hash в store. При одинаковом mtime побеждает лексикографически больший hash. В тесте `AAAA` заменяется на `\x00AAA`; здоровый сосед в итоге тоже содержит `\x00AAA`. Настоящий hardware fault не моделировался: инъекция выполнена записью одного изменённого байта и восстановлением mtime. Эти наблюдения неотличимы от разрешённого внешнего rewrite с сохранением атрибутов, который предыдущий A08 как раз требовал обнаруживать. Поэтому нужен явный выбор контракта: доверенный журнал пользовательских mutations и quarantine/repair для неожиданного mismatch либо документированное отсутствие защиты от silent corruption при произвольных внешних записях. Повторный SHA256 сам по себе не знает, какая копия правильная.

## Проста ли реализация

Инфраструктура компактна: один daemon, SQLite и pull по HTTP. Передача проверяет размер/hash, умеет повторять ошибки, а сохранение tombstones устранило опасный автоматический GC. Эти свойства полезны и подтверждены предыдущими тестами.

Но модель изменения файла остаётся сложной: gateway подтверждает файловую операцию; watcher позже превращает наблюдение в новую запись; syncer отдельно меняет файл и store; repair хранит ещё одно состояние; cleanup может удалить промежуточное состояние без знания о commit. Нет единого durable operation ID, по которому после сбоя можно однозначно определить, какое состояние было подтверждено и какое нужно восстановить.

Общий mutex уменьшил часть interleavings, но не объединил эту семантику. Он также удерживается во время полного hash одного файла и локального WebDAV COPY. [`CheckStorage`](../../internal/watcher/watcher.go) для `/readyz` берёт тот же mutex. Поэтому долгий локальный I/O блокирует независимые commits и readiness; отмена HTTP context ожидание `sync.Mutex` не прерывает. Это вывод по коду, не измеренная нагрузочная авария. Пределы throughput и p95/p99 этим ревью не установлены.

Ещё одна цена текущего подхода: restart меняет incarnation, соседи повторяют metadata stream, а `applyChange` вызывает checksum refresh до проверки победителя. Даже без повторного скачивания одинаковых файлов это может означать повторное чтение их байтов с диска для каждого peer.

## Что упростить до выпуска

1. Ввести единый путь принятия изменения для gateway и репликации: проверка storage, логическая версия изменения, staging, фиксация и понятное recovery. Файловый mtime оставить атрибутом файла.
2. Определить допустимый writable namespace. Самый узкий вариант — обычные файлы без writable aliases, с атомарной публикацией; поддержка произвольных ссылок и внешних writers требует отдельной координации.
3. Удалять временные копии только после установленного исхода операции; по рестарту восстанавливать журнал, прежде чем scanner сможет объявить отсутствующие файлы удалёнными.
4. Сделать идентичность repair уникальной на всё время её жизни и нормализовать peers. Тяжёлое чтение/hash вынести из общего commit mutex с проверкой поколения перед публикацией.
5. Зафиксировать политику mismatch: что считается новым внешним изменением, а что повреждением, и где сохраняется проверенная копия для восстановления.

После этого нужны зелёные приёмочные проверки на перечисленные переходы, crash injection в каждой фазе commit и длительный прогон на целевом storage. Quorum, zero-RPO и сохранение обеих конфликтующих версий остаются отдельными продуктовыми гарантиями; текущая репликация их не предоставляет.

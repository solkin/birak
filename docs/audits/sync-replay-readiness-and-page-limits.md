# Синхронизация нод: replay после рестарта, readiness при активной записи и границы ответа peer

Дата: 2026-09-20. База: `cb813fe`. Проверка «белым ящиком» перед production:
чтение всего пути репликации (`syncer`, `store`, `watcher`, `server`), поиск
условий, при которых синхронизация перестаёт быть безотказной, и закрепление
найденного тестами.

## Оценка

Ядро репликации построено правильно и защищает данные: версия и состояние
фиксируются одной транзакцией, cursor не проходит мимо незаписанного отказа,
скачанные байты проверяются по размеру и SHA256 до публикации, rename идёт
перед записью в SQLite, порядок `CompareState` детерминирован и одинаков в
polling, repair и reconciliation. Порядок блокировок (`paths` → commit lock →
`store.mu`) односторонний, взаимных блокировок нет; `go test -race` чист.

Найденные проблемы лежали не в сохранности данных, а в **непрерывности работы**:
нормальные, самоустраняющиеся состояния трактовались как отказ, а объём работы
после рестарта соседа был пропорционален всему объёму данных. Все четыре случая
воспроизведены тестами, которые падают на `cb813fe` и проходят после правок.

«Простая как молоток» — про эту систему сказать нельзя, и это честная цена
выбранных гарантий. Один поток изменений, очередь repair, сверка манифестов,
логический clock на путь, namespace-тумбстоны, conflict copies, replica intents,
журнал COPY/MOVE и карантин по контрольной сумме — семь независимых механизмов
восстановления. Каждый закрывает документированный отказ, но совокупная модель
состояний велика, и это следует учитывать при эксплуатации и дежурстве.

## Найдено и исправлено

### 1. Запись через gateway помечала ноду как неготовую

`periodicScan` и `processBatch` считали `fileops.ErrBusy` ошибкой сканирования.
Но «занят» означает лишь то, что файл прямо сейчас публикует writer этого же
процесса: staging-файл уже создан, а результат будет проиндексирован в его
собственном commit. Последствия на работающем кластере:

- `/readyz` отдаёт 503, пока идёт перезапись существующего файла, то есть нода
  выводится из балансировщика ровно в момент, когда её используют;
- `last_scan` не обновляется, и `Ready` не восстанавливается до **следующего
  успешного полного scan** — по умолчанию до 5 минут;
- при непрерывном потоке перезаписей почти каждый scan задевает открытый writer,
  и нода может не вернуться в ready вообще;
- если под busy-файл попадает *первый* scan, `ready` не закрывается, и syncer,
  который его ждёт, не стартует до следующего успешного прохода.

Исправление: `ErrBusy` пропускается в обоих местах (имя уже учтено в `onDisk`,
так что проход удалений не затрагивается). Настоящие неисправности —
недоступный каталог, замена файла директорией, повреждение контрольной суммы —
по-прежнему закрывают readiness; это закреплено отдельным тестом.

Тесты: `internal/watcher/writer_readiness_test.go`.

### 2. Рестарт соседа приводил к повторному хешированию всего объёма

Смена incarnation сбрасывает cursor, и peer заново проигрывает весь свой
манифест. `applyChange` вызывал `watcher.RefreshLocked` **до** сравнения
состояний, то есть читал и хешировал локальный файл для каждой записи потока —
включая те, которые у ноды уже есть побайтно. Хеширование идёт под общим commit
lock, который нужен gateway-записям, индексации и остальной репликации.

Измерено на этой машине (macOS arm64, APFS, тёплый кеш — оптимистичная оценка):
replay 32 сошедшихся записей по 4 MiB (128 MiB уже на диске) занимал **118 мс**
чистого перечитывания, худшее ожидание параллельного commit lock — **27.3 мс**.
После правки: **1.16 мс** и **3 мкс**. На реальном диске и файлах в гигабайты
удержание lock масштабируется линейно с размером файла.

Второй, худший эффект: локальная ошибка чтения превращала сошедшееся имя в
вечную строку repair. Файл с правами, недоступными процессу (`0000`, чужой UID
в соседнем контейнере), бесконечно переоткрывался, делая peer `healthy: false`.

Исправление: если индекс уже говорит, что удалённое состояние не выигрывает, и
имя не помещено в карантин — запись пропускается без чтения диска. Это безопасно:
переиндексация может только усилить локальное состояние, но не ослабить его.
Ровно так уже работает `reconcilePage`, так что путь polling стал согласован с
путём reconciliation, а не приобрёл новое правило.

**Осознанный размен, зафиксированный явно.** Обнаружение молча изменившихся байт
при совпадающих размере и времени — задача периодического checksum scan, а не
входящего потока. До правки replay соседа иногда случайно заодно проверял
целостность; это не контроль, а побочный эффект: его частота определялась
рестартами чужого процесса. При `scan_interval` по умолчанию (5 минут) scan
проверяет всё чаще, чем происходят рестарты, поэтому покрытие не уменьшается.
При сильно увеличенном `scan_interval` задержка обнаружения повреждения
становится равной ему — это следует учитывать при выборе значения.
Имя, уже помещённое в карантин, по-прежнему идёт полным путём; тест
`TestQuarantinedNameStillRepairsFromAnEqualPeerState` это закрепляет.

Тесты: `internal/syncer/replay_and_page_limits_test.go`.

### 3. Ответ peer декодировался без ограничения размера

`/changes`, `/manifest` и `/meta` разбирались через `json.NewDecoder(resp.Body)`
без каких-либо границ. Peer — сломанный, скомпрометированный или подменённый
на plain-HTTP участке — единолично решал, сколько памяти выделит сосед.

Воспроизведено: на запрос с `limit=100` peer отдал страницу 42 MiB со 100 000
записей. Нода **приняла и применила** её, выделив **3717 MiB**. Ответ на запрос
и близко не проверялся на соответствие запрошенному объёму.

Исправление: `decodePage` ограничивает чтение бюджетом, пропорциональным числу
запрошенных записей (8 KiB на запись + 1 MiB на обрамление), и отказ выдаётся
по ходу потока — с внятной ошибкой, а не «unexpected end of JSON». Дополнительно
проверяется число записей в странице. После правки та же атака отклоняется,
выделив **8 MiB**, cursor не двигается. Легитимная полная страница из 1000
записей с путями по 400 символов принимается — это тоже закреплено тестом.

### 4. Насыщенный логический clock от peer навсегда блокировал локальную запись

`validateMetadata` ограничивал `Size`, но не `Clock` и не `ModTime`. Принятый
`Clock = MaxInt64` не может быть превзойдён: `PutLocal` после него отдаёт
`conflict clock exhausted` при любой локальной записи по этому имени и по именам
его предков. Вероятность из реального timestamp ничтожна, но проверка стоит
одну строку, а отказ — постоянный. Значение теперь отклоняется как некорректные
metadata.

Остаточное условие: peer, приславший `MaxInt64 - 1`, всё ещё способен довести
путь до насыщения одной локальной записью. Полностью это закрывается только
отдельной политикой валидации/восстановления предельных metadata.

## Что проверено и оставлено без изменений

- **Продвижение cursor.** Все записи store сериализованы одним мьютексом, поэтому
  номер версии и commit атомарны относительно друг друга: читатель `/changes`
  не может увидеть версию N+1 раньше N. Страница проверяется целиком до
  применения, cursor строго растёт, повтор или перестановка страницы уводят
  polling в backoff. Отдельная проверка не понадобилась.
- **Блокировки.** `paths` → commit lock → `store.mu`, слот скачивания берётся
  всегда после `paths`. Цикла нет; медленная загрузка задерживает, но не
  блокирует остальных. `go test -race ./...` чист.
- **Схождение трёх нод.** Дополнительно прогонялись два сценария реальных
  демонов (настоящие fsnotify, таймеры, HTTP, SQLite): шторм конкурентных
  записей и удалений по общим именам с трёх нод, и шторм с переключением имени
  между файлом и директорией плюс гибель и возврат одной ноды в середине. Оба
  сходятся к побайтово одинаковым деревьям; 8 повторов с `-race` — PASS.
  В репозиторий эти проверки не добавлены: параллельно появился
  `internal/syncer/partition_model_test.go`, который покрывает ту же область
  строже и без зависимости от реального времени, а дублировать тайминг-зависимые
  тесты в CI — заведомая нестабильность.

## Границы, которые правками не снимаются

| Граница | Практическое следствие |
| --- | --- |
| Хеширование и локальный COPY держат общий commit lock | Файл в гигабайты удерживает lock на время своего чтения; на это время встают gateway-записи. Периодический scan читает **все** байты каждые `scan_interval` |
| Индексация — одна транзакция `synchronous=FULL` под одним мьютексом | На этой машине ~5900 файлов/с, при 8 писателях ~6400: параллельного масштабирования нет по построению. Это потолок первичного индексирования и приёма мелких файлов |
| У передачи файла нет ограничения по общей длительности | Peer, отдающий по байту раз в 59 секунд, удерживает слот скачивания и блокировку имени неограниченно. Минимальной скорости не проверяется |
| Reconciliation ставит в repair всё расхождение целиком | Сильно отставшая нода получает в очередь копию всего объёма, который и так придёт потоком. Сходится, но с двойной работой и лишними запросами `/meta` |
| Некорректные или игнорируемые metadata отбрасываются молча | Различие в `ignore` между нодами и битые записи не видны ни в `/status`, ни в счётчиках — только в логе |
| Уровень логирования зашит как `Debug` | `cmd/birakd/main.go:52`. Каждая запись файла и каждое движение cursor пишутся в stdout синхронно, причём `store.put` логирует **под** своим мьютексом: залипший сборщик логов останавливает запись метаданных всей ноды. Настройки уровня нет |
| Нет метрик, только JSON `/status` | Мониторинг обязан опрашивать и разбирать `/status`: глобальный `repairs.total`, возраст старейшей операции, `peers[].lag`, ошибки и свежесть scan. `/healthz` и `/readyz` для этого недостаточно |
| Один повреждённый файл закрывает readiness всей ноды | Карантин по контрольной сумме держит `Ready=false`, пока копия не восстановлена с peer. Способа подтвердить и продолжить работу нет |
| Тумбстоны хранятся бессрочно | Метаданные растут с числом различных удалённых имён; манифест для reconciliation растёт вместе с ними |

Для допуска остаются нагрузочный прогон на целевом объёме и размерах файлов,
измеренные p95/p99 клиентских операций и времени сходимости после отказа ноды,
восстановление согласованного backup и жёсткий отказ питания/VM.

## Воспроизведение

Красный прогон — снимок `cb813fe` плюс только новые тестовые файлы:

```sh
go test ./internal/watcher ./internal/syncer -count=1 \
  -run 'TestScanSkipsFileHeldByAWriter|TestEventBatchForAFileBeingWritten|TestConvergedEntry|TestSaturated|TestOversizedPeerPage'
```

Результат до правок: FAIL во всех пяти. Три сопровождающих теста
(`TestGenuineScanFaultStillFailsReadiness`,
`TestQuarantinedNameStillRepairsFromAnEqualPeerState`,
`TestFullPageOfLongNamesIsStillAccepted`) проходят и до, и после — они
стерегут границы правок, а не сами правки.

Зелёный прогон:

```sh
go vet ./...
go test -race -count=1 -timeout 900s ./...
```

Рабочее дерево на момент проверки содержало параллельные изменения
`internal/store/store.go`, `cmd/birakd/main.go`, `README.md` и
`.github/workflows/test.yaml` из другой сессии; прогоны включают их.

# Синхронизация трёх нод: разделение сети и сохранность принятой работы

Дата: 2026-09-20. База: `cb813fe`. Целевое число нод, подтверждённое владельцем:
**3**. Объём данных, размеры файлов, интенсивность записи и допустимые RPO/RTO
не заданы.

## Оценка

Основа репликации хорошо защищает целостность: версия и состояние фиксируются
транзакционно, cursor не проходит мимо несохранённого отказа, скачанные байты
проверяются, незавершённые filesystem commit восстанавливаются. Существующие
тесты проверяют SIGKILL, рестарты, конфликты имён, потерю событий, права доступа
и ошибки хранилища. Новая проверка трёх нод подтверждает сходимость после
комбинации сбоев, а не только каждого сбоя по отдельности.

Безусловную гарантию «безотказно и без задержек» эта архитектура не даёт.
Это асинхронная репликация с разрешением конфликтов, локальным ACK и общей
блокировкой filesystem commit. Итог этой работы — исправление конкретной
потери принятой работы и воспроизводимые проверки; производительность на
целевом объёме и устойчивость к отключению питания ещё требуют испытаний.

## Найдено и исправлено: удаление peer стирало repair queue

При каждом старте daemon вызывал `PruneCursors(cfg.Peers)`. Метод удалял и
курсор, и все repair-строки для отсутствующих в конфигурации адресов. При
пустом списке peers исчезала вся очередь. Это не эквивалентно успешному
выполнению операций: cursor уже мог пройти их версии, а queued tombstone мог
быть последним свидетельством удаления.

До исправления `TestPruneCursorsRetainsAcceptedRepairsAfterReopen` упал в обеих
ветках: удаление одного peer и последнего peer оставляло пустую очередь после
переоткрытия SQLite. Лог: `/tmp/birak-sync-audit-peer-removal-red.log`.

Исправление уменьшает код: `PruneCursors` удаляет только позиции потоков.
Repair-строки, полные metadata и их revision сохраняются. Миграций SQLite,
изменений протокола и новых фоновых циклов нет.

Новый интеграционный тест возвращает адрес в конфигурацию, переоткрывает БД
и запускает настоящий repair scheduler без polling/reconciliation. Файл
восстанавливается, а удаление выполняется даже при 404 `/meta` источника;
очередь опустошается. Это проверяет, что восстановление использует сохранённую
операцию, а не новое событие от peer.

**Эксплуатационная семантика:** очередь отсутствующего в конфигурации URL
приостановлена и остаётся в `/status.repairs.total` и `oldest_age_ms`.
Возвращение того же URL возобновляет работу. Автоматического переназначения
очереди другому адресу нет. Перед окончательным выводом ноды нужно завершить
её операции и проверить сходимость; удаление peer из списка не отменяет их.

## Новая проверка трёх нод

`internal/syncer/partition_model_test.go` использует настоящие HTTP, SQLite и
файловые commit с тремя воспроизводимыми seed: **7, 29, 101**. В каждом:

- 90 локальных операций записи/удаления по 12 именам и исходный файл;
- откат и совпадение mtime, повторные записи и пересоздания;
- изоляция третьей ноды на 50 шагов, продолжение работы остальных;
- ответы 503, оборванные тела файлов и повреждённые JSON-страницы;
- три переоткрытия SQLite с сохранением URL и сменой incarnation;
- страницы `/changes` по три записи и два параллельных скачивания;
- восстановление связности, polling, reconciliation и обработка очередей.

Ожидаемое состояние строится из всей истории подтверждённых локальных
состояний, используя установленный порядок `CompareState`. Проверяются
точные metadata и байты на **каждой** ноде, отсутствие удалённых файлов,
нулевая очередь и отсутствие новых версий при повторе уже сошедшегося обмена.
Тест проверяет применение порядка и восстановление; независимым доказательством
корректности самого comparator он не является.

Планировщик в этом тесте управляется явно: это воспроизводимая проверка
состояний, а не замер времени восстановления production-циклов. Разделение
сети моделируется HTTP 503, а не firewall. Переоткрытие SQLite здесь не
заменяет прежние отдельные тесты настоящего SIGKILL.

## CI и переполнение диска

Раньше обычный CI не задавал `BIRAK_TEST_FULL_VOLUME`, поэтому три настоящих
ENOSPC-сценария пропускались. Workflow теперь создаёт отдельный tmpfs **16 MiB**,
передаёт его тестам и размонтирует после завершения. Сценарии проверяют отказ
до передачи, во время передачи и при заполнении SQLite, затем восстановление.
`-count=1` исключает кешированный результат.

Локальный Linux-прогон использует UID 1000, Go 1.25.14 / Alpine и аналогичный
ограниченный tmpfs. Запуск изменённого workflow на GitHub в эту работу не входит.

## Оставшиеся условия допуска к production

| Граница | Практическое следствие для трёх нод |
| --- | --- |
| ACK подтверждает только локальные filesystem и SQLite | Потеря единственной ноды до передачи данных другим может потерять подтверждённую запись. Три ноды сами по себе не дают quorum или RPO=0 |
| Polling ждёт весь batch | Медленный большой файл задерживает следующую страницу даже при свободных download-слотах. Reconciliation независим, но по умолчанию период равен часу. 60 s — timeout бездействия, не максимальная длительность передачи |
| Проверки hash и локальный COPY используют общий commit lock | Большие файлы и scan могут задерживать gateway-записи. Перезапуск peer вызывает replay текущих metadata и дополнительные проверки локальных файлов |
| Readiness относится к локальному scan/storage | Успешный `/readyz` не означает сходимость. Открытый SFTP writer может временно сделать scan неготовым; это нужно учитывать при выводе ноды из балансировщика |
| Tombstones сохраняются бессрочно | Метаданные растут с числом разных удалённых имён. Это сознательная цена защиты от воскресших файлов |
| Конкурентные записи одного имени разрешаются выбором победителя | Обе версии обычного same-name конфликта не сохраняются. Clock skew может влиять на победителя; структурные конфликты имеют отдельные recovery copies |
| Логический clock ограничен int64 | Параллельный probe воспроизвёл принятие `Clock=MaxInt64` и последующий отказ `PutLocal` с `conflict clock exhausted`. Предельные metadata требуют отдельной политики валидации/восстановления; это исправление данный случай не закрывает |

Для допуска нужны нагрузочный прогон на реальном объёме и размерах файлов,
измеренные p95/p99 клиентских операций и времени сходимости после отказа одной
из трёх нод, восстановление согласованного backup и hard-crash storage/VM.
Эти испытания не заменяются сотнями функциональных тестов. Мониторинг должен
включать **глобальный** `repairs.total`, возраст старейшей операции, peer lag,
ошибки и свежесть scan; только `/healthz` или `/readyz` недостаточно.

## Воспроизведение и результаты

```sh
go vet ./...
go test -race -count=1 -timeout 240s ./...
go test -race -count=5 -shuffle=on \
  -run '^TestPartitionedClusterMatchesAcknowledgedHistory$' \
  -timeout 120s ./internal/syncer
```

Исходный полный набор на macOS: PASS, корневой пакет **76.544 s**.
Новая проверка разделения сети: PASS; пять повторов с `-race -shuffle=on`:
PASS, **56.922 s**, всего 15 запусков трёхнодового сценария.

Во время работы в общем checkout появились параллельные экспериментальные
`zz_probe*`-тесты, и один общий macOS-прогон завершился на них с ошибками.
Это не считается зелёным результатом общего рабочего каталога. Финальный
набор проверяется отдельно: снимок `cb813fe` плюс файлы этой доработки в
`/tmp/birak-release-audit-33dceuk8`. Чужие экспериментальные файлы в снимок
не входят; его успешность ничего не утверждает об их ожиданиях. Параллельные
изменения `watcher.go` и `syncer.go` также не входят в проверенный снимок. Два упавших probe
ожидали успешный replay при правах `000`: текущий код возвращает ошибку чтения
и сохраняет repair. Объявлять такой файл проверенным только по прежней записи
SQLite было бы ослаблением контроля целостности. Стоимость повторного hash —
отдельный вопрос производительности. Probe предельного clock описан выше;
readiness при открытом writer включён в таблицу условий допуска.

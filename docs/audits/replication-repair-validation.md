# Очередь репликации, проверка ответов и реальная нехватка места

## Воспроизведённые и исправленные проблемы

| Проблема | Исправление | Регрессия |
| --- | --- | --- |
| Корректное имя с временно недопустимым локальным путём считалось плохими метаданными. Poll продвигал курсор без repair; retry удалял очередь; reconciliation пропускала файл | Валидация входных метаданных не обращается к файловой системе. Проверка текущего локального пути выполняется под commit lock до чтения watcher; её ошибка сохраняет работу в очереди | Симлинк родителя наружу: poll, repair, reconciliation × загрузка/удаление. Посторонние байты и локальный индекс не затронуты; после повторного открытия SQLite и удаления препятствия очередь завершается без новых изменений на источнике |
| Смена родителя во время HTTP-загрузки позволяла создать staging вне корня или в `.birak`; проверка после чтения watcher также могла принять приватные байты за более новую локальную версию и очистить repair | Путь повторно проверяется под namespace lock перед созданием staging и до чтения локального состояния при публикации. Удаление также проверяет путь после получения lock | Настоящий HTTP и смена namespace под общим lock: после получения заголовков либо перед чтением body; ссылка наружу либо в `.birak`. Запрещены staging в защищённой цели, индексирование чужих байтов и потеря repair; повтор после устранения ссылки успешен |
| Более новый некорректный ответ `/meta` мог вытеснить принятую операцию и очистить repair. Имя ответа молча заменялось запрошенным, позволяя применить удаление другого файла | Ответ должен содержать точно запрошенное имя и корректные метаданные до сравнения состояний | Настоящий HTTP: неправильный hash либо tombstone другого имени с большим clock. Принятая работа остаётся; после исправления ответа повтор получает ожидаемые байты и очищает очередь |
| Открытие FIFO в `/files` удерживало HTTP handler после отключения клиента | Проверка обычного файла до и после неблокирующего открытия; атрибуты берутся с открытого дескриптора | Настоящий FIFO и HTTP-запрос с deadline: немедленный 400 вместо ожидания writer |

Первоначальные воспроизведения запущены до исправлений и завершились FAIL:
`/tmp/birak-sixth-red.log`. Дополнительно проверены явно настроенное исключение
для ранее принятой repair-операции, NUL в имени и scratch-каталоги среди родителей.
Отдельное воспроизведение смены родителя до исправления:
`/tmp/birak-sixth-path-race-red.log` — FAIL в трёх из четырёх сочетаний;
в том числе фактическое создание временного файла снаружи корня.

Статическая проверка имён сохраняет запрет traversal, неканонических имён,
приватного каталога и scratch. Настроенные `ignore` остаются основанием пропустить
операцию; временная проблема локальной файловой системы — основанием повторить её.
Проверка ответа `/meta` независима от локальной конфигурации исключений.
Ранее принятые удаления по-прежнему могут выполняться при недоступном источнике.

## Реальный ENOSPC

`TestDiskFullReplicationRecoversAfterReopen` использует реальный HTTP, SQLite и
непривилегированного пользователя Linux. Выделенный tmpfs размером 16 MiB
заполняется до настоящего `ENOSPC`. Тест отказывается заполнять не-tmpfs,
том вне диапазона 1–64 MiB или работать от root.

| Сценарий | Проверяемое поведение |
| --- | --- |
| Том данных полностью заполнен до загрузки | Старые байты и метаданные сохранены; операция целиком записана в repair перед продвижением курсора |
| Место заканчивается во время загрузки | После заполнения освобождаются 64 KiB под файл размером 88 KiB; запись staging получает настоящий ENOSPC. Старый файл сохранён; ошибка загрузки остаётся в repair |
| Заполнен отдельный том SQLite | Ошибка записи не скрыта; курсор остаётся на предыдущей позиции; прежнее содержимое и метаданные не изменены |

В каждом случае место освобождается, SQLite закрывается и открывается заново.
При заполнении данных работа восстанавливается из сохранённой очереди;
при заполнении SQLite поток повторяется с непродвинутого курсора.
Проверяются точные байты, состояние метаданных и пустая очередь в конце.
Обычный тестовый запуск без `BIRAK_TEST_FULL_VOLUME` пропускает этот тест.

Воспроизведение из корня репозитория (Docker; исходники подключаются read-only,
сборка и данные находятся внутри удаляемого контейнера):

```sh
docker run --rm --tmpfs /limited:rw,size=16m,mode=1777 \
  -v "$PWD:/source:ro" golang:1.25-alpine sh -ec '
    apk add --no-cache gcc musl-dev
    adduser -D -u 1000 tester
    mkdir -p /work/src
    cp -R /source/cmd /source/internal /source/go.mod /source/go.sum /source/*_test.go /work/src/
    chown -R tester:tester /work
    su tester -s /bin/sh -c "cd /work/src && GOCACHE=/work/cache GOPATH=/work/go BIRAK_TEST_FULL_VOLUME=/limited go test -race -count=1 -timeout 120s -v -run ^TestDiskFullReplicationRecoversAfterReopen ./internal/syncer"
  '
```

Для полного прогона в том же окружении заменить последнюю команду Go на
`go test -race -count=1 -timeout 240s ./...`, сохранив переменные окружения.

Протокол остаётся **3**, схема SQLite не меняется. Восстановление требует
устранить реальную причину отказа: очередь сохраняет работу, но не освобождает
место и не удаляет мешающие пользовательские объекты самостоятельно.

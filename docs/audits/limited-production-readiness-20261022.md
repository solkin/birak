# Готовность к ограниченной эксплуатации

Исправления и повторная оценка — в [отчёте после исправлений](limited-production-fixes-20261022.md)
(выпуск v2.1.0). Ниже сохранён исходный результат проверки.

Дата: 2026-10-22. База: `31e0095`, выпуск v2.0.4. Код не менялся: это
проверка перед допуском, а не заход с исправлениями.

Целевая нагрузка взята из review от 2026-10-12: около 10 TB APK (10–500 MiB)
и иконок, 1–2 млн имён, три ноды. Часть нод периодически отключается. Клиенты
ходят через S3 и HTTP UI за nginx с TLS. Проверялись четыре направления:
безопасность внешних поверхностей, корректность репликации и хранилища,
эксплуатация (поставка, наблюдаемость, жизненный цикл) и клиентский путь
данных. Воспроизведения шли на копиях репозитория с настоящими процессами
`birakd`: macOS arm64/APFS, Linux arm64 в Docker, nginx 1.27 с конфигом из
`deploy/`, клиенты curl и aws-sdk-go-v2.

## Оценка

**Ядро репликации готово, поставка и края — нет.** В текущем виде
(`docker-compose.yml`, `.env.example`, пример nginx) допуск давать нельзя. Он
становится возможным после четырёх небольших правок кода (F1–F3, F6) и
эксплуатационных условий из раздела «Условия допуска».

Ни одна из находок не ломает основной контракт синхронизации. Подтверждено
повторно:

- целостность продолжения загрузок;
- фильтрация replay;
- защита от размонтирования корня;
- восстановление после SIGKILL;
- согласованные ETag на разных нодах;
- откат 2.0.4 → 2.0.3 → 2.0.4.

Опасные места лежат на стыке с окружением. Это S3-операция, которую шлюз не
реализует, но отвечает на неё 200; учётные данные, которые отказывают в
открытую сторону; файлы, которые демон не может прочитать; поддеревья, которые
пропадают целиком.

P1 — исправить до запуска. Для условных P1 указано, когда они срабатывают.
P2 — допустима временная эксплуатационная мера, но закрыть нужно до
расширения нагрузки. P3 — низкий приоритет.

## Подтверждённые проблемы

### F1 P1 S3 CopyObject обнуляет объект и отвечает 200

`x-amz-copy-source` нигде не обрабатывается. `PUT` с этим заголовком уходит
в `handlePutObject` ([s3.go:307](../../internal/gateway/s3/s3.go),
[handlers.go:776](../../internal/gateway/s3/handlers.go)) и публикует пустое
тело. `aws s3 cp s3://apk/a s3://apk/b` обнуляет `b`. Приём «скопировать в
себя с `--metadata-directive REPLACE`», которым обычно правят Content-Type,
обнуляет сам APK. Обнуление затем реплицируется на все ноды. UploadPartCopy
так же кладёт пустую часть.

Воспроизведено дважды. До копирования HEAD показывает `Content-Length: 1048576`.
Копирование отвечает `200`. После него HEAD показывает `Content-Length: 0`.

Исправление: при `x-amz-copy-source` в PutObject и UploadPart отвечать
`501 NotImplemented` до чтения тела. В Sebastian обработки этого заголовка тоже
нет. Скорее всего, там та же ошибка; это нужно проверить отдельно.

### F2 P1 Пустые и половинчатые учётные данные открывают шлюзы

[`authenticate`](../../internal/gateway/s3/s3.go) и
[`CheckBasicAuth`](../../internal/gateway/gateway.go) пропускают всех, если
пусты оба поля. Если пусто одно, пустая строка используется как настоящий
секрет. `applyEnv` игнорирует пустые переменные. `SecurityWarnings`
предупреждает только при обоих пустых полях. Поставка усиливает каждый из
этих эффектов:

- Если в `.env` нет `S3_ACCESS_KEY` и `S3_SECRET_KEY`, compose подставляет `""`.
  S3 и HTTP UI стартуют без аутентификации, через nginx получаются публичные
  PUT и DELETE. Воспроизведено: анонимный PUT поверх APK вернул 200,
  `POST /_api/delete` удалил каталог.
- Если задан access key, а secret пуст, любой, кто знает access key, подписывает
  запросы пустым секретом. Access key виден в каждом presigned URL.
  Воспроизведено: `curl --aws-sigv4 … --user "changeme-access-key:"`, PUT 200,
  DELETE 204. Предупреждения в логе нет.
- Если задан username, а пароль пуст, вход `admin` с пустым паролем проходит в
  HTTP UI, WebDAV и SFTP. `.env.example` задаёт `HTTP_USERNAME=admin`.
- `docker-compose.yml` не передаёт в контейнер `BIRAK_CLUSTER_SECRET` и
  `BIRAK_PEERS`. Секрет из `.env` молча теряется. Если раскомментировать
  `9100:9100`, как подсказывает комментарий, peer API отдаёт все файлы без
  секрета.

Исправление:

- В `validate()` отказывать в старте, если у включённого шлюза пусто хотя бы
  одно поле. Исключение — явный `allow_anonymous: true`.
- В compose использовать `${VAR:?}` для всех учётных данных и явно передавать
  `BIRAK_CLUSTER_SECRET`, `BIRAK_PEERS`, `BIRAK_LOG_LEVEL`.
- Отказывать в старте на значениях `changeme*`.

### F3 P1 Один нечитаемый файл выключает ноду, а после рестарта и репликацию

`EACCES`/`EPERM` при скане не входят в `unindexable`
([watcher.go:1170-1177](../../internal/watcher/watcher.go)). Поэтому sweep
никогда не завершается, нода остаётся unready навсегда, и ERROR пишется раз в
`scan_interval`. После рестарта первый скан тоже не завершается, а syncer
бесконечно ждёт `watcher.Ready()`
([syncer.go:293-301](../../internal/syncer/syncer.go)). Шлюзы при этом
принимают записи (S3 PUT → 200), и подтверждённые записи не реплицируются
никогда. Нечитаемый каталог при старте даёт `fatal: recover storage: … permission
denied`, и `restart: unless-stopped` уходит в бесконечный цикл рестартов.

Типичный путь: `sudo rsync`/`cp` в bind-mount оставляет файл root 0600. README
сам предлагает класть файлы через `cp` и `rsync`.

Воспроизведено независимо в двух направлениях проверки (`chmod 000` на файл и
на каталог, macOS и Linux):

- `birak_local_ready 0`;
- `birak_last_scan_seconds` отсутствует;
- в логе нет ни одной строки «syncer started».

Исправление: считать `EACCES`/`EPERM` на отдельном имени пропуском
(`skipped{reason="unreadable"}`), без вывода удаления. Опасность
файлов чужого владельца описать в README.

### F4 P1 условно: пропавшее вложенное поддерево удаляется на всём кластере

Условие: под `sync_dir` есть отдельный mount, symlink на другой диск или
union FS (mergerfs).

Защита от потери тома проверяет только sentinel в корне. `ENOENT` для любого
файла ниже корня становится tombstone
([watcher.go:734-744](../../internal/watcher/watcher.go)); комментарий там
прямо говорит «absence is a local deletion, not loss of a mount». Удаление
выводят sweep, scrub и событийный путь. `CleanEmptyParentsLocked` вдобавок
удаляет пустую точку монтирования.

Воспроизведено на трёх нодах. 20 APK лежали на образе, смонтированном в
`n1/sync/apks`. После размонтирования через 15 с на всех нодах `apks=0`, все
ноды `ready`, в логах по 20 «file deletion synced» без единого предупреждения.
При старте с размонтированным поддеревом удаление проходит за 6 с. Если
диск жив, повторное монтирование возвращает файлы. Если диск умер, копий не
остаётся ни на одной ноде. Контрольная проверка: размонтирование самого корня
корректно даёт unready при работе и fatal при старте.

Тот же путь срабатывает при ошибочном `rm -rf` или неполном rsync/restore. Это
свойство синхронизации без версий, а не ошибка. Но предохранителя от массового
удаления нет совсем.

Исправление:

- Запоминать `st_dev` каталогов и не выводить удаления под каталогом, чей
  device отличается от корня или изменился.
- Не удалять пустые точки монтирования.
- Добавить предохранитель: если один проход хочет удалить больше N файлов или
  X% живых, проход останавливается, нода становится unready и ждёт
  подтверждения оператора.

Без исправления: `sync_dir` должен быть одной ФС без вложенных mount и
symlink, нужен алерт на падение `birak_files` и снапшоты.

### F5 P1 условно: peer-трафик идёт открытым текстом

Условие: ноды связаны через WAN без VPN.

У peer listener нет TLS ([main.go:178-198](../../cmd/birakd/main.go)).
`X-Birak-Secret` уходит в каждом запросе, а SHA-256 файла заявляет тот же peer.
Наблюдатель на пути видит секрет и затем читает все файлы. MITM может подменить
`/changes` и `/files`, и подменённый APK будет принят и разослан дальше.
Перехват секрета подтверждён через `nc -l`. Подмена выведена из кода.

Клиент syncer уже поддерживает `https://` peer URL: системные CA, редиректы
отклоняются, proxy из окружения не используется.

Исправление: WireGuard/VPN либо TLS-прокси перед `:9100` — без изменений кода.
Позже — `tls_cert_file`/`tls_key_file` для peer listener и предупреждение о
`http://` на не-приватный адрес.

### F6 P2 Одинаковый `node_id` молча делит кластер

Значение по умолчанию — `node-1`, и в конфиге, и в compose. Две ноды из одного
шаблона отвергают ответы друг друга (`peer has duplicate node_id`). При этом
обе `ready`, обе принимают записи через LB, и данные расходятся. Сигналы — только
`birak_peer_healthy=0` и WARN. После исправления ID ноды сходятся без потерь.
Воспроизведено.

Исправление: не стартовать с непустым `peers` и `node_id`, равным пустому
значению или `node-1`.

### F7 P2 Рекурсивное удаление через UI или WebDAV останавливает все записи ноды

Удаление дерева индексирует каждый файл под общим commit lock
([fileops.go:324](../../internal/fileops/fileops.go),
[commits.go:89-170](../../internal/watcher/commits.go)). Каталог из 300 тыс.
файлов удалялся 280 с. Параллельный S3 PUT пяти байт ждал 280 с; чтения не
пострадали. Это около 0.9 мс на файл. WebDAV MOVE/COPY деревьев идут тем же
путём; их время не замерялось.

Мера: не удалять большие деревья через UI/WebDAV, оставить WebDAV
выключенным. Исправление: удалять ограниченными пачками.

### F8 P2 Остановка совпадает с grace-периодом Docker

У всех серверов один `shutdownCtx` на 10 с
([main.go:333-358](../../cmd/birakd/main.go)), и этот же срок Docker ждёт по
умолчанию. Любая незавершённая отдача APK держит остановку все 10 с. Получается
гонка с SIGKILL: каждый деплой может пройти через восстановление после краша.
Восстановление проверено, но это лишний риск. Замер: SIGTERM при медленной
загрузке → выход через 10.1 с. С `docker stop -t 60` — exit 0, без него — 137.

Мера: `stop_grace_period: 30s` в compose. Исправление: дренаж не дольше
5–8 с, затем `Close()`.

### F9 P2 Пример nginx неверен для APK-нагрузки

[`nginx.birak.conf.example`](../../deploy/nginx.birak.conf.example):

- `proxy_buffering` включён по умолчанию. Скачивание 500 MiB медленным
  клиентом спулится на диск nginx: при целевом egress это до ~10 TB записи
  в сутки.
- Нет `keepalive` к upstream, поэтому новое TCP-соединение на каждую иконку
  (около 21 тыс. TIME_WAIT).
- `proxy_pass http://birak:…` резолвится один раз. После пересоздания
  контейнера — 502 до `nginx -s reload`.
- Маршрутизации по `/readyz` нет. Гарантия «новая реплика не попадает в
  балансировщик» в поставляемом деплое не работает.

Все четыре пункта воспроизведены. Исправление:

- `proxy_buffering off`;
- `upstream { keepalive 64; }` и `proxy_set_header Connection ""`;
- `resolver 127.0.0.11 valid=10s` и `proxy_pass` через переменную;
- описанный способ исключать неготовую ноду (haproxy или проверка `/readyz`).

### F10 P2 У шлюзов нет таймаутов на тело запроса и ответ

Есть только `ReadHeaderTimeout` и `IdleTimeout`. 50 PUT, отправивших 1 байт,
через 135 с держат 50 горутин, около 150 fd и 50 temp-файлов. 20 GET с
нечитающим клиентом держатся больше 190 с. За nginx (`client_body_timeout`,
`send_timeout`) полностью замолчавший клиент отрезается, а клиент, отдающий по
капле, держит ресурсы без ограничения. Исправление: продлеваемые
`SetReadDeadline`/`SetWriteDeadline` через `http.ResponseController`.

### F11 P2 Access-лог на каждый запрос без ротации

На уровне INFO пишется строка на каждый запрос, около 167 байт. При 1000
GET/с иконок это 14–30 ГБ в сутки на ноду. В compose нет `logging:`, и
json-file по умолчанию не ротируется. В строке нет latency и
`X-Forwarded-For`. Мера: `logging: {driver: local, options: {max-size: 100m,
max-file: "5"}}`.

### F12 P2 Пробелы наблюдаемости

- Нет метрики свободного места для sync и meta; документация не говорит, что
  нужен node_exporter. При полном диске нода остаётся `ready`, а записи шлюзов
  падают.
- Нет счётчиков запросов и 5xx по шлюзам.
- Версию не видно: нет `-version`, `build_info`, версии в `/status`.
- `/metrics` закрыт тем же `cluster_secret`, который открывает чтение всех
  файлов.
- `birak_last_scan_seconds` отсутствует до первого успешного скана, поэтому
  алерт на возраст молчит именно в случае F3.
- `birak_peer_last_success_seconds` равен 0 у peer, который ни разу не ответил.
- Списки алертов в README и `production-readiness.md` не содержат
  `birak_local_ready` и `birak_storage_ok`.

### F13 P2 Список большого каталога в HTTP UI съедает память

`/_api/list` на каждую страницу читает и lstat-ит весь каталог
([httpui/handlers.go:75-90](../../internal/gateway/httpui/handlers.go)).
Каталог из 300 тыс. файлов: 0.7–0.8 с на страницу. 8 параллельных запросов
подняли RSS с 168 до 901 МБ. Плоский каталог иконок на 1–2 млн имён в UI —
это риск OOM для всей ноды вместе с S3. Мера: не открывать такие каталоги в UI.

### F14 P2 Потеря meta проходит молча, первичная индексация долгая

Если потерян named volume `birak-meta` (`compose down -v`, другое имя
проекта), нода без предупреждения создаёт новую БД, привязывается к
существующему `storage-id` и переиндексирует всё. Очередь repair пропадает.
Пока первый скан не закончился, в логе на уровне INFO нет прогресса.

Замер: 50 тыс. файлов индексируются за 68 с на Linux. Экстраполяция на
1.5 млн имён — от 35 минут до 2.5 часа плюс хеширование 10 TB.

Исправление:

- WARN или отказ при пустой БД и существующем `storage-id`, с явным флагом
  переиндексации;
- лог прогресса индексации.

### F15 P2 Ключ-«папка» ломает загрузки под префиксом

`PUT apk/releases/` с пустым телом создаёт 0-байтовый файл `releases`, после
чего каждый `PUT apk/releases/*.apk` получает 500. Так создают папки AWS
console, Cyberduck, S3 Browser и rclone с directory markers. Исправление:
ключ на `/` с пустым телом — mkdir или 200 без записи.

## Что проверено и в порядке

- Полный `go test -race -count=1 ./...` и `go vet` на macOS arm64 прошли.
  Тулчейн Go 1.27.2 — локальный, новее закреплённого. CI тега v2.0.4 зелёный,
  включая Linux race/ENOSPC и четырёхнодовую Docker-приёмку.
- govulncheck на релизном Go 1.26.10: 0 достижимых уязвимостей в исходниках и
  в бинаре. На локальном Go 1.27.2 достижима GO-2026-6809 (crypto/x509,
  исправлена в 1.27.3). Собирать только закреплённым тулчейном.
- Peer API: все endpoints, кроме `/healthz` и `/readyz`, под секретом.
  Сравнение constant-time.
- SigV4: header-форма, presigned, aws-chunked с цепочкой подписей, проверка
  digest в PutObject и DeleteObjects.
- Пути: `..`, `.birak`, scratch, symlink escape, multipart staging.
- HTTP UI: XSS, CSP, CSRF за nginx. SFTP: только subsystem sftp. Секреты
  не попадают в логи.
- Продолжение загрузок: итоговый SHA-256 считается по фактическим байтам,
  If-Range/ETag работают, неверные байты не публикуются.
- Фильтр `newerThanLocal` и ревизии очереди не теряют работу. Новая реплика
  при `max_repair_queue` меньше числа имён сходится.
- Размонтирование корня: unready при работе, fatal при старте. Потеря meta при
  целых данных не делает старые файлы новее кластерных.
- Обрывы PUT, UploadPart, UI-upload и GET (сотни штук) не оставляют fd,
  горутин и temp-файлов. Частичный объект не публикуется.
- Перезапись 500 MiB во время чтения: читатель получает старые байты целиком.
- 20 параллельных PUT одного ключа дают ровно одну загрузку.
- Range, 304, 416 работают. ETag и Last-Modified совпадают на разных нодах.
- ListObjectsV2 на ~400 тыс. ключей: 13–22 мс на страницу в начале и в глубине.
- Complete на 500 MiB держит только свою загрузку.
- `max_upload_bytes` действует на всех путях.
- Ошибочная конфигурация и занятый порт дают exit 1. Lease не пускает второй
  процесс.
- Откат 2.0.4 → 2.0.3 → 2.0.4 на тех же данных работает.

## Условия допуска

Код (небольшие правки):

1. F1 — `501` на `x-amz-copy-source`.
2. F2 — отказ в старте при пустых и половинчатых учётных данных; `${VAR:?}`
   и передача `BIRAK_CLUSTER_SECRET`/`BIRAK_PEERS` в compose.
3. F3 — `EACCES`/`EPERM` на имени считаются пропуском, а не отказом ноды.
4. F6 — отказ в старте с peers и `node_id` по умолчанию.

Эксплуатация (без кода):

5. Peer-трафик только через VPN или TLS-прокси (F5).
6. `sync_dir` — одна ФС без вложенных mount и symlink. Регулярные снапшоты
   data+meta+`storage-id`, восстановление проверено (F4, F21).
7. Compose:
   - тег `2.0.4` вместо `latest`;
   - `stop_grace_period: 30s`;
   - ротация логов;
   - WebDAV и SFTP выключены, если не нужны (F8, F11).
8. nginx: `proxy_buffering off`, keepalive, resolver, исключение неготовой ноды
   по `/readyz` (F9).
9. Алерты:
   - `/readyz`;
   - `birak_local_ready`, `birak_storage_ok`;
   - `birak_peer_healthy`, `birak_repair_oldest_seconds`;
   - `birak_quarantined_files`;
   - падение `birak_files`;
   - свободное место через node_exporter (F12).
10. В HTTP UI не удалять большие деревья и не открывать огромные плоские
    каталоги (F7, F13).
11. Остаётся из [production-readiness](../production-readiness.md): soak на
    целевых дисках и uplink, проверка отказа питания.

Сразу после запуска — F4 (`st_dev` и предохранитель от массового удаления):
это главное, чего не хватает до свойства «надёжная как молоток».

## Воспроизведение

```sh
# F1: CopyObject обнуляет объект (S3 без учётных данных, только loopback)
curl -X PUT --data-binary @app.bin http://127.0.0.1:39200/apk/app.apk
curl -X PUT -H "x-amz-copy-source: apk/app.apk" \
  -H "x-amz-metadata-directive: REPLACE" -H "Content-Length: 0" \
  http://127.0.0.1:39200/apk/app.apk                 # 200
curl -sI http://127.0.0.1:39200/apk/app.apk | grep -i content-length   # 0

# F2: compose без .env
docker compose config | grep -E 'BIRAK_(S3_ACCESS|CLUSTER)'
# access key без secret
curl --aws-sigv4 aws:amz:us-east-1:s3 --user "changeme-access-key:" \
  -X PUT --data-binary EVIL http://127.0.0.1:9200/apk/app.apk     # 200

# F3: нечитаемый файл
chmod 000 "$SYNC/apk/locked.apk"; curl -i http://127.0.0.1:9100/readyz   # 503 навсегда

# F4: вложенный mount (Linux)
mount /dev/sdX1 "$SYNC/apks"; # дождаться репликации
umount "$SYNC/apks"           # через scan_interval: tombstones на всех нодах
```

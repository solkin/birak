# Проверка синхронизации перед production — исходный аудит

Дата: 2026-09-19. Исходный commit: `e454e389234d2cd5a8bb859e60d20a6185aeb6d9`.

**Исторический отчёт.** Ниже сохранены результаты до исправлений на указанном commit, включая старые номера строк и команды запуска. Найденные A01–A10 исправлены; приёмочные тесты включены в обычный CI. Актуальные изменения, проверки и ограничения: [отчёт об исправлениях](sync-reliability-fixes.md).

**Исходный вердикт: проверенную реализацию нельзя считать готовой к production с требованиями сохранности данных и гарантированной сходимости.** Обычная репликация и восстановление после простоя работают, но воспроизведены потеря более свежей записи, ложные удаления, потеря работы при продвижении курсора и зависание загрузки. Прохождение штатных тестов этих гарантий не подтверждает.

На момент аудита изменения содержали только тесты и этот отчёт; рабочая реализация ещё не была исправлена. Приёмочные тесты запускались с build tag `syncaudit`, чтобы воспроизвести небезопасное поведение отдельно от обычного CI. После исправлений этот build tag удалён.

**Что проверено**

Изучены `syncer`, `watcher`, SQLite store, peer API, запуск/остановка daemon и связь с файловыми gateway. Проверки выполнены на macOS arm64, Go 1.27.0, и в Linux arm64 / Alpine 3.21 под непривилегированным UID 1000. Linux-бинарники собраны тем же Go с `CGO_ENABLED=0`; Linux-прогоны выполнены без race detector. Сетевая связь в тестах — loopback, данные — временные каталоги.

| --- | --- |
| Полный штатный набор `go test -race -count=1 -timeout 180s ./...` | PASS, корневой пакет 58.257 s; обнаруженных data race нет |
| `go vet ./...` и `go vet -tags syncaudit ./...` | PASS |
| Девять существующих `TestReliability_*`, `-race -shuffle=on -count=10` | PASS, 90 запусков сценариев |

| Новые быстрые приёмочные проверки, `-race -short -count=10` | 12 сценариев стабильно FAIL, каждый 10/10; два контрольных сценария PASS |
| Те же быстрые приёмочные проверки на Linux | Те же 12 FAIL, два PASS |

В новых тестах всего 16 сценариев: 13 FAIL и три PASS, включая отдельный процессный тест. `-short` пропускает только длинную проверку ожидания заголовков. В macOS-прогоне процессного теста `-race` инструментирует тестовый harness; дочерний daemon собирается обычным `go build`.

Процессный сценарий сначала синхронизирует 128 файлов, убивает второй daemon через `SIGKILL`, затем меняет 32 файла, удаляет 32 и создаёт 64 на работающем узле. После запуска второго процесса с прежними `sync_dir` и `meta_dir` сверяются байты всех 160 итоговых файлов, отсутствие лишних файлов, пустая очередь repairs и состояние peers. Это подтверждает восстановление после **падения процесса** при таком профиле нагрузки; отключение питания этим не моделируется.

**A01 — ошибка чтения становится удалением.** В `watcher.go:609` ошибка `WalkDir` только логируется, после чего отсутствие имени в `onDisk` трактуется как удаление (`699–724`). В тесте достаточно временно убрать права на подкаталог: файл остаётся на диске, но в SQLite появляется tombstone. Соседи вправе удалить свои исправные копии. Недоступность корня даёт тот же эффект сразу для всего индекса. Нужны признак успешного полного обхода, запрет вывода об удалении для недоступных поддеревьев и проверка доступности ожидаемого storage root. После ошибки первоначального сканирования нельзя сообщать о готовности для применения удалённых изменений.

**A02 — потеря новой локальной записи.** `applyChange` читает метаданные до сетевого запроса (`syncer.go:484`), а затем `downloadAndApply` без повторной проверки делает `Rename` и `PutFile` (`897–917`). Mutex принадлежит только syncer: gateway и watcher его не используют. Тест останавливает загрузку, записывает и индексирует локальную версию с timestamp 300, затем разрешает загрузку удалённой версии 200. На диске остаётся версия 200. Нужен единый механизм публикации для gateway/syncer/watcher с повторной проверкой поколения перед commit. Для прямых внешних записей в filesystem следует отдельно определить конфликтное поведение и сохранять конфликтующие версии: один внутренний mutex не обеспечивает взаимного исключения с произвольным внешним процессом.

**A03 — нарушена связь «курсор → применено или надёжно сохранено».** `applyBatch` при отмене context оставляет часть batch необработанной и не ставит её в repair (`422–439`). Ошибка `EnqueueRepair` лишь логируется (`451–453`). `syncBatch` в обоих случаях сохраняет `batchMax` (`400`). Получено: `cursor=2, pending=0` при двух неприменённых файлах; при инъекции ошибки SQLite enqueue — `cursor=1, pending=0, err=nil`. Repair-fault вводится SQL trigger, без повреждения настоящей БД. Нужны возврат ошибки из batch и запрет продвижения мимо несохранённой работы либо транзакционная запись полноценного durable inbox вместе с курсором. Reconciliation может позже исправить часть последствий, если исходная запись ещё существует; это не подтверждение надёжности очереди.

**A04 — подтверждение чтения не означает подтверждение применения.** Курсор проходит мимо неудачного удаления; следующий `/changes?since=N` подтверждает его источнику. Источник после TTL удаляет tombstone. Repair хранит имя/version, но не само состояние удаления; получив `/meta` 404, `repairOne` удаляет задание (`syncer.go:554–561`). В тесте peer постоянно онлайн, временно запрещено удаление через права каталога, TTL сжат до наносекунды. После восстановления прав старый файл сохраняется, восстановить удаление уже неоткуда. Операционное правило «пересоздавать ноду после простоя дольше TTL» этот случай не закрывает. Нужны отдельные подтверждения применения/безопасного сохранения полного состояния и проверяемый протокол GC. Самый простой безопасный первый выпуск — не очищать tombstones автоматически, пока этот протокол не реализован.

**A05 — одинаковые байты не означают одинаковую версию.** `applyChange:489` и `reconcilePage:702` пропускают одинаковые hash/deleted до сравнения timestamps. Watcher делает то же (`552`, `800`). Доставка `X@100 → X@300 → Y@200` оставляет `Y@200`, тогда как другой порядок оставляет `X@300`. Проверены все шесть перестановок. Полная сверка может вылечить часть случаев, пока узел с `X@300` доступен непосредственно, но промежуточная нода уже потеряла информацию о старшей версии и не передаст её дальше. Обновление содержимого можно пропускать; принятие старшей версии и её распространение — нельзя. Это относится и к повторным tombstones с разными timestamps.

**A06 — забытая история удаления.** `remoteWins` возвращает false для tombstone при `local == nil` (`syncer.go:980–983`). Новая или промежуточная нода получает удаление, но не сохраняет его. Следующая доставка старых байтов принимается как новый файл. Исправление — сохранять применимые tombstones даже без локального файла; отдельно проверять распространение удалений через цепочку узлов. Полносвязность и дальнейшая сверка могут временно маскировать дефект, а пропуск удаления промежуточной нодой нарушает транзитивную репликацию.

**A07 — ограничена только часть сетевой операции.** Watchdog запускается после `downloadClient.Do` (`793`, `834`). У клиента нет общего deadline, а в transport отсутствуют `ResponseHeaderTimeout` и `TLSHandshakeTimeout`. Проверка с настоящим HTTP server показала, что отсутствие headers не приводит к завершению даже после 76 s; выход произошёл только после отмены тестом. Подтверждено также, что watchdog тела ответа сам по себе работает. Нужны раздельные ограничения connect/TLS/headers и inactivity для тела, без короткого общего лимита на большой файл. [Поля transport в документации Go](https://pkg.go.dev/net/http#Transport).

**A08 — full scan не является проверкой целостности.** `compareScanBatch` пропускает hash при совпадении mtime/size (`watcher.go:786–790`). Тест заменяет `original` на `replaced`, сохраняет timestamp и выполняет три сканирования: индекс остаётся со старым hash. Такое возможно после offline restore и при изменениях с сохранением атрибутов; peer reconciliation сравнивает индексы, а не байты. Нужен отдельный периодический checksum scrub, в том числе после некорректной остановки/восстановления, со счётчиком и временем последней успешной проверки. Полный hash на каждом обычном проходе может быть слишком дорог; частоту scrub следует задавать отдельно.

**A09 — курсор не переживает GC монотонно.** Следующая version восстанавливается через `MAX(version)` среди оставшихся файлов (`store.go:112`). После удаления последних tombstones и restart epoch прежний, счётчик снова начинается с 1. В тесте старый cursor=5 видит только один из шести новых файлов: новые version 1–5 уже пропущены, а max=6 скрывает откат от `needsCursorReset`. Reconciliation может исправить пропуск позднее. Нужно хранить high-water counter отдельно, транзакционно с изменением записи, и определить epoch для восстановления из backup: обычная копия старой БД сохраняет прежний epoch.

**A10 — подтверждения не учитывают переинициализацию потребителя.** `RecordAck` сохраняет `MAX(old, new)` (`store.go:489`). После потери metadata и запроса `since=0` источник продолжает видеть ack=100. Нужна идентичность инкарнации потребителя в протоколе подтверждений и сброс gate при новой инкарнации. Простое уменьшение ack на каждом запросе само по себе не решает переупорядочивание запросов и повторное использование node ID.

**Дополнительные ограничения по коду, не выдаваемые за воспроизведённую аварию**

- SQLite работает в `WAL + synchronous=NORMAL` (`store.go:85`). Это защищает от повреждения WAL при штатных предпосылках SQLite, но последний commit может откатиться после потери питания/падения ОС. SIGKILL процесса этого не проверяет. Для обязательной долговечности подтверждённых метаданных нужен обоснованный выбор `FULL` и отдельный тест storage crash. [Документация SQLite](https://sqlite.org/pragma.html#pragma_synchronous).
- `applyDeletion` не синхронизирует удаление directory entry, а `syncDirEntry` после rename только логирует ошибку на debug-уровне. Создание цепочки новых родительских каталогов также не снабжено полной цепочкой fsync. Поэтому комментарии о безусловном порядке durability «disk перед store» сильнее фактической реализации.
- Gateway подтверждают локальную файловую операцию до завершения репликации; нет quorum write/read, cluster-wide transaction или zero-RPO гарантии. Потеря единственной ноды до передачи свежей записи соседям может означать потерю записи. Репликация не заменяет резервную копию, поскольку распространяет удаления.
- Mtime — одновременно файловый атрибут и конфликтные часы. Сдвиг часов, восстановленный timestamp, права/режим без изменения байтов и конфликт «файл против каталога» требуют явно описанного контракта. Разрешение конкурирующих данных по hash детерминировано, но не сохраняет обе пользовательские версии.
- Конфигурация допускает одинаковые `node_id` на разных нодах; уникальность не проверяется между peers, хотя ack keyed by node ID. Один node ID по умолчанию особенно требует проверки при развёртывании.
- `reconcile_interval: 0` документирован как отключение, но `syncer.New` заменяет `<=0` на час. Согласовать конфигурацию, предупреждение и фактическое поведение.
- `/status` полезен, но `healthy` не учитывает ошибки filesystem scan, давность удачного scrub или сбои первоначальной индексации. `lag=0` означает потребление metadata stream, а не равенство файлов. Нет полноценного readiness, подтверждающего исправность локального storage и завершение успешного initial scan.

**Простота и эксплуатационная устойчивость**

Основа компактна и понятна: один процесс, SQLite, pull по HTTP, отдельные loops для polling/repair/reconcile, hash-check перед публикацией. Уже есть атомарный rename, ограничение объёма скачиваемых байтов, защита путей, backoff, постоянная очередь repairs и наблюдаемость прогресса. Для небольшого кластера это разумная база.

Сложность сосредоточена в независимых авторах состояния: watcher, gateway, syncer, repair и GC принимают решения по частично разным представлениям о файле. Добавление отдельных повторов не устраняет эту проблему. Полезное упрощение — единый путь принятия версии и commit, отдельный durable inbox с полным состоянием операции и явный протокол подтверждений. Файловое mtime лучше отделить от версии репликации; выбор логических/гибридных часов потребует миграции протокола и самостоятельной проверки.

Полносвязный кластер имеет `N×(N−1)` направлений polling и сравнения манифестов. Лимит downloads задан на peer, плюс отдельный repair worker; общего бюджета I/O на ноду нет. Полный scan хранит `onDisk` для всех имён и накапливает события до конца прохода. Это риски масштабирования, выведенные из кода, а не измеренный предел производительности. Нагрузочные показатели для миллионов файлов и больших объектов этим аудитом не установлены.

**Порядок подготовки к выпуску**

1. Закрыть ложные удаления, перезапись новой версии и небезопасное продвижение курсора; добавить ограничения всех стадий сетевого запроса.
2. Сохранять tombstones неизвестных путей, распространять старшие версии с теми же байтами, сделать version counter долговечным. До надёжного ACK/GC сохранять tombstones.
3. Определить гарантию успешной записи: локальная долговечность или подтверждение реплик, допустимая потеря при аварии, конфликтная политика, правила restore и offline rejoin. Привести README к реально обеспеченному контракту.
4. Добавить scrub и readiness, затем сделать все 16 приёмочных сценариев зелёными и включить их в CI без скрывающего build tag.
5. Провести отдельный длительный прогон на целевом образе/Go/архитектуре: network partition в обе стороны, ENOSPC/EIO, ограниченная память, hard crash VM/storage, clock skew, большие деревья и объекты, upgrade/backup restore, конкурентная запись через все gateway. Измерять p95/p99 времени сходимости, throughput, память, возраст repairs и время последнего успешного scan/scrub.

Отказоустойчивость после простого рестарта подтверждена. Безопасность перечисленных аварийных переходов — опровергнута конкретными тестами. Обещания README о гарантированной сходимости и отсутствии потерянной работы сейчас не следует использовать как основание для production SLA.

**Воспроизведение**

Все команды ниже запускаются из корня репозитория. Аудитные проверки должны завершаться ненулевым кодом до исправления дефектов. Permission-сценарии требуют непривилегированного пользователя и явно skip при запуске от root.

```sh
go test -race -count=1 -timeout 180s ./...
go vet ./...
go vet -tags syncaudit ./...
go test -race -shuffle=on -count=10 -timeout 180s -run TestReliability ./...

# Быстрые воспроизведения: 12 падающих сценариев, 2 контрольных PASS, 1 SKIP.
go test -race -tags syncaudit -short -run TestAudit -count=1 -timeout 30s -v \
  ./internal/syncer ./internal/watcher ./internal/store

# Реальный timeout, около 76 секунд.
go test -race -tags syncaudit -run TestAuditSlowHeaders -count=1 -timeout 90s -v ./internal/syncer

# Реальные процессы и сохранённые данные после SIGKILL.
go test -race -tags syncaudit -run TestAuditProcess -count=3 -timeout 120s -v .
```

Для процессного теста можно передать абсолютный путь готового daemon через `BIRAK_AUDIT_BINARY`; иначе тест сам собирает его из текущего дерева. Временные узлы автоматически останавливаются, их каталоги удаляются.

```sh
mkdir -p /tmp/birak-audit-linux
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go test -c -tags syncaudit -o /tmp/birak-audit-linux/ ./...
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -o /tmp/birak-audit-linux/birakd ./cmd/birakd
docker run --rm --network none --user 1000:1000 \
  -e BIRAK_AUDIT_BINARY=/tests/birakd \
  -v /tmp/birak-audit-linux:/tests:ro alpine:3.21 \
  /tests/birak.test -test.run TestAuditProcess -test.count 3 -test.timeout 120s -test.v
```

В Docker `--network none` сохраняет loopback: тестовые ноды общаются только внутри контейнера. Для amd64 нужно соответственно изменить `GOARCH` и использовать совместимый образ/хост.

# Нагрузочный стенд и проверка аварийным завершением

Дата: 2026-09-20. База: ветка `sync-production-readiness`, коммит `1b67613`.
Стенд: `bench_test.go`, запуск описан в README («Load stand»).

## Зачем

Все предыдущие проверки отвечали на вопрос «правильно ли». Стенд отвечает на
те, которые и решают допуск к production и которые функциональными тестами не
закрываются: сколько стоит запись, пока нода проверяет саму себя, за сколько
peer догоняет после отказа, и остаётся ли нода при этом ready.

Три фазы: заполнение и первичная индексация; непрерывная запись в одну ноду,
пока идёт скраб и реплицирует сосед; отказ соседа, запись в его отсутствие,
возврат и замер сходимости. Сходимость проверяется по **отпечатку манифеста**
(имя, хеш, состояние, clock, размер), а не по числу файлов: отказ, в котором
переписывались существующие имена, число файлов не меняет.

Отчёт начинается со **стоимости публикации на этой файловой системе** — голый
цикл «write, fsync, rename, fsync каталога». Без этой калибровки задержка
записи не интерпретируема: непонятно, это цена Birak или цена диска.

## Результат на macOS arm64 / APFS / NVMe

Конфигурация: 200 файлов по 16 KiB, один файл 16 MiB, 10 секунд записи,
скраб 4 MiB/с.

| Показатель | Значение |
| --- | --- |
| Стоимость публикации на ФС | **9.7 мс** |
| Задержка записи Birak, 1 писатель | p50 **45.8 мс**, p95 67 мс, p99 79 мс |
| Задержка записи Birak, 4 писателя | p50 **160 мс**, p95 207 мс, p99 225 мс |
| Пропускная способность записи | **~25 операций/с** — одинаково при 1 и при 4 писателях |
| Ожидание общего commit lock, 1 писатель | p50 24 мс |
| Первичная индексация | ~160 файлов/с |
| Сходимость после возврата ноды | 2.4–3.6 с на ~350 файлов |
| Отказы readiness под нагрузкой | **0** |

## Что из этого следует

**1. Запись сериализована полностью.** Пропускная способность не меняется при
росте числа писателей с 1 до 4, а задержка растёт линейно (45.8 мс → 160 мс,
ровно в четыре раза). Это подпись одной глобальной блокировки: конкуренция не
добавляет пропускной способности, она добавляет очередь.

**2. Скраб здесь ни при чём.** Прогон с `BIRAK_BENCH_SCRUB=0` даёт те же
25 операций/с и ту же задержку. Бюджетный скраб свою работу делает — он не
мешает записи.

**3. Запись стоит примерно в 4.7 раза дороже минимума этой ФС** (45.8 мс против
9.7 мс). Разница — в том, что commit индексирует имя **дважды**: `Begin`
наблюдает старое поколение до перезаписи, `Finish` индексирует результат.
Каждый проход — хеш, `fsync` файла, `fsync` родительского каталога и
транзакция SQLite с `synchronous=FULL`. Получается порядка шести fsync там, где
безопасная публикация требует двух. При измеренных ~5.9 мс на fsync это
объясняет наблюдаемые 45 мс почти полностью.

**4. Уровень 2 закрыл только половину.** Хеширование вынесено из-под общей
блокировки для *скана*. Путь commit по-прежнему хеширует под ней, причём
дважды, и для перезаписи большого файла `Begin` читает всё старое содержимое
до того, как запись вообще будет принята. На гигабайтном файле это тот самый
stall, который считался устранённым.

## Что сделано по этим выводам

Три правки, все на пути commit, ни одна не меняет гарантий.

**Индексация больше не fsync-ает то, что commit уже сделал долговечным.**
Проверено, что это верно для всех путей публикации: `closeWriter`, `Publish`,
`Rename`, `Remove`, WebDAV COPY через `copyFile` и MOVE через `ReplaceLocked` —
каждый fsync-ает байты до rename. Повторный fsync в `refreshFileLocked` остался
только для внешнего писателя, который мог не синхронизировать ничего.

**Staged-байты синхронизируются и хешируются до взятия блокировки.**
Временный файл принадлежит одному писателю, менять его некому, а rename
сохраняет inode — значит, снятые с него stat и хеш описывают опубликованный
файл точно. Результат передаётся индексатору через `fileops.Published`, и
`inspectFile` принимает его, пока поколение совпадает.

**`Begin` не перечитывает старое поколение, если stat не изменился.** Та же
логика, что уже работает в дешёвом обходе: совпали размер и время — читать
нечего. Подмена с сохранением обоих остаётся работой скраба.

Вместо трёх булевых параметров у индексации появился один `indexOptions` —
«что вызывающий уже гарантирует». Обещания в нём может дать только commit;
по умолчанию индексация по-прежнему никому не верит.

## Результат правок

Конфигурация **другая, чем в первой таблице**, и её числа с ней не сравниваются:
к стенду добавлен отдельный писатель, непрерывно перезаписывающий файлы по
32 MiB, — иначе цена работы под общей блокировкой ничем не создаётся. 200 файлов
по 16 KiB, два файла по 32 MiB, 15 секунд, один писатель мелких файлов,
скраб 4 MiB/с. Оба прогона — на одном диске, подряд.

| Показатель | До | После |
| --- | --- | --- |
| Задержка записи p50 | 73.8 мс | **46.0 мс** |
| Задержка записи p95 | 135 мс | **83.7 мс** |
| Ожидание общего commit lock p50 | 55.6 мс | **27.5 мс** |
| Пропускная способность | 13 оп/с | **20 оп/с** |
| Перезапись файла 32 MiB p50 | 117.9 мс | 125.1 мс |

Задержка самой большой записи не изменилась — и не должна была. Работа никуда
не делась, она вынесена из-под общей блокировки: fsync и хеш 32 MiB по-прежнему
входят в её собственную задержку. Выигрыш достался всем остальным, и видно его
в ожидании блокировки: оно упало вдвое, а обычная запись — на 38%.

Чтобы убрать и этот проход, писателю пришлось бы хешировать поток по мере
записи. `OpenWriter` отдаёт наружу `*os.File`, которым SFTP пользуется через
`WriteAt`, так что обёртка-хешер туда не встаёт без отдельной переработки
интерфейса.

Осталось три транзакции SQLite с `synchronous=FULL` на запись: `BeginLocal`,
`PutLocal` и `EndLocal`. Это и есть основная оставшаяся разница с 9.8 мс
минимума. `EndLocal` долговечности не требует — потерянное при отказе намерение
лишь заставит переиндексировать имя при старте, — но менять `synchronous`
поштучно означает отдельное соединение и отдельный набор проверок.

## Поправка: вывод про SQLite был неверным

Написанное выше — «запись стоит в 4.7 раза дороже минимума ФС, и основная
оставшаяся статья это три транзакции `synchronous=FULL`» — **не подтвердилось
измерением**. Замер по частям на том же диске:

| Операция | Время |
| --- | --- |
| `store.BeginLocal` | 72 мкс |
| `store.PutLocal` | 184 мкс |
| `store.EndLocal` | 73 мкс |
| `store.GetFile` / `HasLocalIntent` | 12 / 6 мкс |
| `watcher.checkStorageLocked` | 41 мкс |
| `os.Create` + запись 16 KiB + `Sync` | **4.7 мс** |
| Полная запись через `fileops`, ничего параллельно | **11.7 мс** |

Все три транзакции вместе — **0.33 мс**, меньше процента записи. Дорого стоит
fsync файла, а не метаданных.

Ошибка была в самом стенде: «стоимость публикации на ФС» он мерил в тишине, а
задержку записи — под нагрузкой. Сравнивать их напрямую нельзя, а отчёт именно
к этому и подталкивал. Теперь в отчёте три строки, и между ними видно, что есть
что:

```
publish floor        11.3 мс   цена файловой системы
write, node idle     14.2 мс   + собственные издержки Birak (~3 мс, 26%)
write, under load    60.0 мс   + очередь на единственной блокировке тома
```

Собственные издержки Birak на запись — около 26% поверх файловой системы, а не
4.7 раза. Всё остальное, что видно под нагрузкой, — **ожидание в очереди**, и
единственный способ это изменить — перестать сериализовать записи одной
блокировкой на том.

## Другие хрупкие места, найденные при этом разборе

**Скан держал в памяти имя каждого файла.** Проход удалений сравнивал индекс с
множеством всех имён на диске. На дереве в десять миллионов файлов это больше
гигабайта, который выделяет фоновая задача, — отказ ровно в тот момент, когда
нода занята. Множество убрано: проход удалений идёт по индексу постранично и
проверяет каждое имя одним `stat`. Памяти — страница, работы — вдвое больше
дешёвых `stat`, что для обхода приемлемо.

**`Store.AllFiles` загружал всю таблицу в память.** Помечен Deprecated, в
рабочем коде не использовался, но оставался готовой к вызову ловушкой. Удалён;
тест переписан на постраничный `ListNonDeleted`.

**Открытие файла без усечения копировало его целиком под общей блокировкой.**
Худший из оставшихся stall: SFTP-клиент, открывающий гигабайтный файл на дозапись,
останавливал все записи на ноде на время копии. Копия вынесена из-под
блокировки — писатель регистрируется до её снятия, поэтому назначение уже
занято для всех остальных commit, а внешнюю подмену по-прежнему ловит проверка
поколения при публикации. `TestSeedingDoesNotHoldTheCommitLock`: до правки
блокировка была доступна **0 раз** за копирование 64 MiB, после — десятки.

## Куда смотреть дальше

- **Сериализация записи** — теперь это единственная крупная статья. Пропускная
  способность не растёт с числом писателей: одна блокировка на том. Разделение
  по поддеревьям — большая и опасная работа; браться за неё имеет смысл только
  с числами этого стенда на целевом железе.
- **Хешировать поток по мере записи**, чтобы большая запись не читала свои же
  байты второй раз. Упирается в то, что `OpenWriter` отдаёт голый `*os.File`.
- **`synchronous=FULL` на macOS не равен долговечности при отказе питания**:
  Go вызывает `fsync`, а APFS сбрасывает кеш диска только по `F_FULLFSYNC`.
  Числа выше сняты на macOS; на Linux соотношение сохранится, абсолютные
  значения — нет. Проверять надо на целевой ФС.

## Как это проверено

`go vet ./...` и `go test -race -count=1 ./...` — зелёные. Корневой пакет
дополнительно прогнан 6 раз подряд без `-race` и 4 раза с ним: один отказ,
случившийся сразу после правки, больше не воспроизвёлся ни разу за 13 прогонов,
и его текст не был сохранён — считать его объяснённым нельзя. Четыре новых теста в
`internal/watcher/commit_indexing_test.go` закрепляют механику: commit
использует уже прочитанные байты (доказывается хешем-часовым), подсказка от
другого поколения отбрасывается, реальная запись через `OpenWriter`
индексируется тем, что лежит на диске, а поколение, которого индекс никогда не
видел, по-прежнему читается целиком.

Утверждение «каждый путь публикации fsync-ает байты до rename» проверено
чтением кода, а не тестом: `closeWriter`, `Publish`, `Rename`, `Remove`,
`copyFile` в WebDAV COPY и `ReplaceLocked` в MOVE. Отказ питания в unit-тесте
не воспроизводится, поэтому это остаётся утверждением ревью — и требованием к
любому новому пути публикации.

Побочный эффект переноса fsync из-под блокировки: если commit потом
отказывается (destination изменился под нами), прочитанные и захешированные
байты пропадают зря. Это редкий случай — требуется конкурентная внешняя
подмена, — и он стоит дешевле, чем удержание блокировки на каждой записи.

## Замечено, но не исправлено

- **Сверка проходит весь манифест каждого peer раз в час.** На десяти миллионах
  имён это десять тысяч запросов в час на peer и столько же пакетных обращений
  к индексу. Для целевых трёх нод это вопрос объёма данных, а не кода.
- **`/status` и `/metrics` считают очередь полным проходом** (`COUNT`, `SUM`,
  `MIN` без индекса по `first_seen`). При очереди в сто тысяч строк и опросе
  раз в 15 секунд это приемлемо, при большем — стоит кешировать на секунду.
- **`log_level: debug` по-прежнему пишет синхронно из горячего пути.** Уровень
  по умолчанию `info` это снимает, но при включённом debug залипший сборщик
  логов по-прежнему тормозит ноду.
- **Один отказ корневого пакета**, случившийся сразу после перехода на единый
  путь применения, не воспроизвёлся ни разу за 13 последующих прогонов, и его
  текст не сохранён. Объяснённым считать нельзя.

## Чего стенд не измеряет

Протокольные издержки (S3/WebDAV/SFTP поверх HTTP), поведение на сетевом томе,
отказ питания, восстановление из backup, и сходимость на канале с реальной
задержкой. Передача, которая продолжает двигаться, общего дедлайна не имеет, —
ни одно число отсюда не ограничивает отставание репликации на медленной линии.

# Раунд 3: сериализация измерена, остальное исправлено

Дата: 2026-09-20.

## Сериализация: число есть, редизайна нет

Добавлен учёт удержания общей блокировки — `fileops.LockStats`, и он же вышел
в `/metrics`. Это то число, которого не хватало: график задержек не отличает
«нода медленная» от «нода сериализована», а чинится это в совершенно разных
местах.

Замер на прежней конфигурации стенда: блокировка держалась **19.7 с за прогон
в 35 с**, то есть 56% времени, в среднем **6.47 мс** на захват. Разбор того,
что внутри, показал два fsync каталога вместо одного: `fn()` синхронизировал
каталог сразу после rename, а затем `Finish` синхронизировал его же ещё раз.
Второй убран тем же правилом `durable`, которым раньше убрали повторный fsync
файла.

После правки: **4.50 мс** среднего удержания (было 6.47), худшее **55.8 мс**
(было 98.9), принятых записей 26/с против 11/с в сопоставимом прогоне.

Оставшееся удержание — почти целиком **один fsync каталога после rename**, и он
неустраним внутри commit: каталог должен стать долговечным до того, как индекс
запишет, что файл существует, иначе после отказа получится «в индексе есть, на
диске нет» и следующий скан разошлёт удаление. Потолок тома при таком
устройстве — порядка 200 commit в секунду, и **никакая микрооптимизация этого
не меняет**.

Единственный способ пройти дальше — параллелизм: блокировка по каталогам для
файловых commit и глобальная эксклюзивная для операций над пространством имён
(rename между каталогами, замена файла директорией, рекурсивное удаление).
Это выполнимо и понятно, но требует классифицировать все 16 мест взятия
блокировки, а ошибка в классификации — это тихое повреждение данных, которое
тесты могут не поймать. **Не сделано намеренно.** Браться стоит отдельной
работой и с числами этого стенда на целевом железе: если там потолок тома
оказывается выше требуемой нагрузки, делать этого не нужно вовсе.

## Флейк найден и исправлен

`TestReliability_SupersededVersionDoesNotBlockStream` ждал появления `b.txt`, а
проверял содержимое `a.txt`. Записи одной страницы применяются параллельно,
поэтому появление одной ничего не говорит о другой. Тест воспроизвёл отказ на
втором из двенадцати прогонов с сохранённым выводом; после правки — 25 прогонов
подряд чисто. Это тот самый отказ, который в прошлом раунде остался
необъяснённым.

Поведение продукта здесь не менялось: `applyBatch` тоже применял страницу
параллельно. Переход на очередь лишь сместил тайминг достаточно, чтобы гонка в
тесте стала заметной.

## Остальное

**Логирование больше не может остановить ноду.** `internal/logging` — обёртка
над `slog.Handler` с очередью фиксированного размера: записи уходят пишущей
горутине, а потребитель, переставший читать, приводит к отбрасыванию записей со
счётчиком, а не к остановке той горутины, которая логировала — обычно
удерживающей общую блокировку. Отброшенное сообщается в лог и на выходе. Это
делает `log_level: debug` пригодным для диагностики в проде.

**Сводки очереди больше не сканируются на каждый опрос.** `/status` и
`/metrics` спрашивают их по таймеру, а ответ стоит прохода по всей очереди —
дороже всего именно тогда, когда очередь велика. Ответ запоминается и
сбрасывается **любой записью в очередь**, а не по сроку годности: первый
вариант с TTL сломал read-your-writes, что и поймал существующий тест. Запрос к
БД идёт без удерживаемого мьютекса, а счётчик поколений не даёт медленному
читателю записать уже устаревший ответ.

**Сверка манифестов возобновляема.** Позиция сохраняется на каждый peer,
`reconcile_page_budget` (64 страницы по умолчанию) ограничивает один проход,
завершённый цикл начинает следующий с начала. Большое дерево сравнивается
непрерывно, а не всплеском раз в час, и прерванный проход не начинается заново.
`0` сохраняет прежнее поведение — весь манифест за один проход.

**`Store.AllFiles` удалён**, проход удалений в скане больше не держит в памяти
имя каждого файла (см. раунд 2).

## Что осталось

- **Сериализация записи** — описана выше, решение отложено осознанно.
- **Хешировать поток по мере записи**, чтобы большая запись не читала свои же
  байты второй раз. Упирается в то, что `OpenWriter` отдаёт голый `*os.File`.
- **RPO ≠ 0** и бессрочные тумбстоуны — продуктовые решения, не дефекты.

# Раунд 4: проверка аварийным завершением, и что она нашла

Дата: 2026-09-21.

## Стенд

`crash_test.go` запускает настоящий процесс демона, убивает его посреди приёма
записей и после перезапуска требует двух вещей:

- **индекс не опережает диск.** Каждое живое имя в индексе обязано лежать на
  диске с записанными размером и контрольной суммой. Запись об отсутствующем
  файле — это не локальная неприятность: следующий скан читает её как удаление
  и рассылает по всем peer.
- **подтверждённая запись существует.** Каждый PUT, на который демон ответил
  2xx, лежит на диске ровно теми байтами, которые отправил клиент.

Второй тест делает то же с двумя нодами: одна принимает записи, вторую убивают
посреди репликации, снова и снова.

Результат: **25 аварийных остановок одной ноды** и **25 остановок реплики во
время репликации, 1246 подтверждённых записей** — инвариант не нарушился ни
разу, реплика получила всё.

Чего стенд не проверяет: SIGKILL оставляет page cache нетронутым, ядро дописывает
всё, что демон ему отдал. Это проверка порядка операций и восстановления, а не
физики fsync. Для отказа питания нужен слой, который умеет терять записи, — на
macOS его нет.

## Найдено ревью: потолок очереди был O(n²)

Проверка «есть ли место ещё для одного имени» выполняла `COUNT(*)` по очереди
на **каждую новую строку**. Поскольку после перехода на единый путь применения
каждое изменение из потока проходит через очередь, массовая синхронизация
становилась квадратичной.

Измерено: при включённом потолке скорость постановки падала с 5783/с до 475/с
к десяти тысячам строк — последняя тысяча в **12.2 раза** медленнее первой. При
выключенном потолке деградации не было вовсе, что и указало на причину.

Исправлено счётчиком в памяти: длина очереди на peer поддерживается инкрементно,
считается один раз при открытии БД и правится при каждой вставке и удалении.
После правки деградации нет (последняя тысяча — 0.9 от первой), а `/status` и
`/metrics` отвечают на «сколько в очереди» из счётчика, а не запросом.

Это тот случай, когда исправление одной проблемы создало другую: потолок очереди
защищал диск от неограниченного роста, а платой оказалась квадратичная вставка
на том самом пути, который я перед этим сделал основным. Нашлось ревью
собственного диффа, а не тестом — функциональные тесты работают на десятках
строк, где квадратичность невидима.

## Мелочи из того же ревью

- **`BatchLimit` без значения по умолчанию.** Страница отвергается, если несёт
  больше записей, чем запрошено; при нулевом лимите это отвергало бы любую
  непустую страницу. Конфигурация требует положительного значения, так что
  в проде это не срабатывало, но ловушка для прямого использования пакета
  оставалась. Теперь `New` подставляет 1000, как и для других лимитов.
- **Затенение `info` в `closeWriter`**: внутренний `info` из `Snapshot`
  перекрывал внешний stat назначения. Работало правильно, читалось скверно.

## Что ещё нашло ревью

**Логирование могло уронить процесс при остановке.** `Close` закрывал очередь,
а `Handle` в неё отправлял — запись, сделанная после `Close` (например,
отложенным шагом завершения), давала «send on closed channel», то есть панику.
Из-за строки в логе, в пакете, который существует ровно чтобы строка в логе
ничего не ломала. Теперь очередь не закрывается никогда: пишущей горутине
подаётся сигнал остановки, она дописывает накопленное и выходит, а поздние
записи молча отбрасываются. Воспроизведено тестом до правки.

**Тихая нода писала строку в лог каждую минуту.** Скраб на пустом дереве
завершает цикл при каждом взгляде. Теперь сообщение о завершённом цикле
выводится, только если цикл что-то действительно проверил.

**Позиция сверки копилась на каждый URL peer.** `PruneCursors` убирал курсоры,
но не эти строки: ротация списка peer оставляла их навсегда. Теперь позиции
удаляются вместе с peer, а принятая работа по-прежнему сохраняется — это
разные вещи.

**Скорость скраба читалась без синхронизации.** Сеттер, который тихо гоняется
с читающим циклом, — это ловушка, а не настройка. Поле стало атомарным.

# Раунд 5: восстановление из резервной копии

Дата: 2026-09-21.

## Найдено: тихое воскрешение удалённых файлов

Написан тест, которого не было: остановить ноду, снять копию обеих директорий,
продолжить писать, восстановить копию поверх ноды и потребовать, чтобы она
вернулась в кластер. Первый вариант теста **упал**: удалённый файл вернулся из
резервной копии и разошёлся обратно на вторую ноду.

Причина оказалась не в коде, а в том, как копировались директории.
**`cp -R` не сохраняет время модификации.** Разрешение конфликтов ранжирует
файл логическим clock, который начинается от его времени модификации, поэтому
восстановленный файл со свежей меткой индексируется как совершенно новая
локальная запись. Дальше он выигрывает у всего, что держит кластер, — включая
тумбстоун, — и перезаписывает это на **каждой** ноде. Ни одной ошибки нигде.

Проверено на живых демонах: с `cp -R` удалённый файл воскресает и расходится по
кластеру; с `cp -pR` тумбстоун выигрывает, и файл остаётся удалённым везде.

Это не дефект репликации, а **требование к процедуре резервного копирования**,
которого не было в документации. Оно добавлено в README отдельным абзацем с
конкретными инструментами: `cp -a`, `rsync -a`, `tar -p` — и явным указанием,
что обычного `cp -R` достаточно, чтобы испортить кластер с одной ноды.

## Сделано: нода теперь говорит об этом вслух

Молчаливость здесь и есть главная опасность, поэтому добавлена проверка: при
первом обходе после старта считаются файлы, чьи **байты совпадают с индексом, а
время модификации — нет**. Восемь и больше таких файлов — это уже не «кто-то
сделал touch», а восстановленная копия без меток времени, и нода пишет
предупреждение, называющее причину и способ исправления, пока ещё есть время
восстановить правильно. Один тронутый файл предупреждения не вызывает; оба
случая закреплены тестами.

## Сделано: сама процедура теперь проверяется

`backup_test.go` выполняет операцию целиком на настоящих демонах: копия обеих
директорий при остановленной ноде, продолжение записи, восстановление,
возвращение в кластер. Проверяется, что восстановленная нода догоняет всё, что
забыла, что вторая нода ничего не теряет, что индекс не опережает диск, и что
новые записи продолжают до неё доходить. Второй тест закрепляет, что резервная
копия, снятая до удаления, удалённый файл не возвращает.

## Результат соака

60 аварийных остановок одной ноды, **32 222 подтверждённых записи** — индекс ни
разу не опередил диск, ни одна подтверждённая запись не пропала. Отдельно
60 остановок реплики во время репликации, 2 972 подтверждённых записи — реплика
сошлась со всеми.

## Ещё из ревью: «последняя сверка» означала не то

После введения бюджета страниц `reconcileOnce` стал возвращаться, не дойдя до
конца манифеста, а `/status.peers[].last_reconcile_ms_ago` обновлялся при каждом
таком возврате. Оператор, смотрящий на это число, считал бы, что кластер сверен,
когда сверена была лишь его часть. Теперь отметка ставится только завершённым
циклом, а «ни разу» отличается от «только что»: `-1` вместо нуля. То же сделано
для возраста цикла скраба.

# Исправления надёжности синхронизации

Дата: 2026-09-19. Изменения относительно `e454e389234d2cd5a8bb859e60d20a6185aeb6d9`.

**Дополнение после повторной проверки:** этот отчёт фиксирует первый набор исправлений, а не общий допуск к production. Обнаружены новые непокрытые аварийные переходы; актуальный вердикт и воспроизведения — в [повторном ревью](replication-second-review.md).

Все десять групп воспроизведённых дефектов A01–A10 из [исходного аудита](sync-production-readiness.md) исправлены. Прежние падающие приёмочные сценарии включены в обычный набор тестов без `syncaudit`. Добавлены проверки конкурентной публикации gateway, открытого SFTP handle, восстановления repair/state из SQLite, готовности storage и восстановления backup.

Это исправление протокола асинхронной файловой репликации, а не добавление quorum или гарантии zero-RPO. Результаты ниже подтверждают конкретные аварийные переходы и восстановление после падения процесса; они не заменяют испытания целевого storage и нагрузки.

## Что изменилось

| Дефект | Исправление | Проверка |
| --- | --- | --- |
| A01: ложное удаление после ошибки обхода или потери root | Неуспешный обход блокирует deletion pass; перед индексированием/применением проверяется привязка root через `.birak/storage-id`; readiness открывается только после успешного scan | Недоступный подкаталог, отсутствующий и заменённый root, ошибка initial scan |
| A02: загрузка затирает свежую локальную запись | Общий commit lock для watcher, gateway и syncer; индексирование текущих байтов и повторное разрешение конфликта после загрузки | Более новая индексированная и ещё не индексированная запись во время download; открытый SFTP writer |
| A03: курсор проходит мимо несохранённой работы | `applyBatch` возвращает ошибки; отмена и ошибка записи repair блокируют продвижение cursor | Отмена batch и SQL trigger, запрещающий enqueue |
| A04: источник очищает ещё не применённое удаление | Автоматический tombstone GC отключён; repair хранит полное состояние и revision; принятый tombstone применяется при 404 и при недоступности источника | Permission failure + принудительный GC источника; offline repair; reopen БД и конкурентное обновление queue |
| A05: одинаковый hash теряет старший timestamp | Единый порядок состояний; обновление mtime/store при одинаковых байтах без повторного download | Все шесть порядков доставки трёх конфликтующих состояний; mtime-only изменение watcher |
| A06: неизвестный tombstone забывается | История удаления сохраняется даже без локального файла | Удаление до первого появления файла и последующая устаревшая запись |
| A07: бесконечное ожидание HTTP headers | Connect/TLS: 10 s, headers: 15 s, body inactivity: 60 s; большого общего deadline нет | Настоящий HTTP peer не отправляет headers; отдельный body watchdog |
| A08: rewrite с прежними size/mtime невидим | Каждый начальный и периодический scan читает SHA256 всех видимых обычных файлов | Offline rewrite с сохранением атрибутов |
| A09: повторное использование version после GC/restart | `last_version` хранится отдельно от файлов и обновляется с ними в одной транзакции; wire incarnation меняется при каждом старте | GC/reopen, rollback неудачного PutFile, restore backup с последующим превышением прежнего cursor |
| A10: высокий ACK переживает сброс потребителя | Сохраняется последнее наблюдение, включая 0, и incarnation потребителя; ACK старой incarnation источника считается 0; ACK не разрешает GC | Сброс ACK в store и через HTTP, запрос со старым epoch |

Дополнительно SQLite переведён на `WAL + synchronous=FULL`. Ошибки fsync файла/каталога возвращаются вызывающему коду. Публикации и удаления синхронизируют родительские каталоги до изменения метаданных; файловые gateway используют общие операции commit. SFTP удерживает защиту открытого writable inode до fsync/close. Очистка пустых каталогов не удаляет временные файлы активной загрузки.

Убраны временные `MarkSynced`-метки и callback записи watcher в store: watcher сам индексирует свежее состояние под общим lock. Большие сетевые загрузки lock не удерживают. Полные scans больше не накапливают пакет устаревших метаданных до конца обхода; в памяти остаётся набор имён для поиска удалений.

Появились `/readyz` и `/status.local`: успешность и возраст последнего scan, ошибка локального storage. `/healthz` остаётся liveness. Замена индексированного файла неподдерживаемым типом делает scan неготовым и не рассылает ложное удаление. Peer с таким же `node_id`, как у локальной ноды, отклоняется в polling, reconciliation, metadata fetch и download. `reconcile_interval: 0` теперь действительно отключает сверку.

## Проверки

В файлах регрессий 28 сценариев, включая исходные 16. Полный штатный набор также проверяет S3, WebDAV, SFTP, HTTP UI, multipart и многоузловую репликацию. Процессный тест собирает дочерний daemon с `-race` и проверяет его журнал на сообщения race detector.

| Прогон | Результат |
| --- | --- |
| macOS arm64, Go 1.27.0: `go test -race -count=1 -timeout 240s ./...` | PASS, корневой пакет 72.182 s |
| Linux arm64 / Alpine, Go 1.25.14 из `golang:1.25-alpine`, UID 1000: тот же полный набор с `-race` | PASS, корневой пакет 63.801 s |
| `go test -race -shuffle=on -short -count=10 -timeout 120s ./internal/store ./internal/syncer ./internal/watcher ./internal/server` | PASS, 10 повторов каждого теста; случайный порядок |
| `go vet ./...`, `git diff --check` | PASS |

Linux-проверка использует toolchain из Dockerfile. Permission-сценарии выполняются под UID 1000, поэтому запрет чтения/удаления действительно действует. Рабочие каталоги тестов временные; production storage не используется. `-short` пропускает только длительную проверку 15-секундного ожидания headers среди новых сценариев.

Процессный сценарий: два настоящих daemon, 128 исходных файлов; `SIGKILL` второго; 32 обновления, 32 удаления и 64 создания на первом; restart второго с прежними данными и SQLite. После восстановления проверяются точные байты всех 160 итоговых файлов, отсутствие лишних файлов, нулевой backlog и состояние peer stream.

CI запускает `go vet` и весь набор с `-race` и timeout 240 s. Для локального воспроизведения:

```sh
go vet ./...
go test -race -count=1 -timeout 240s ./...
go test -race -shuffle=on -short -count=10 -timeout 120s \
  ./internal/store ./internal/syncer ./internal/watcher ./internal/server
```

## Эксплуатационные изменения

- Tombstones больше не очищаются по TTL. `sync.tombstone_ttl` сохранён для совместимости конфигурации, но не управляет GC. Размер метаданных растёт с числом разных удалённых имён. Возвращение давно отключённой ноды не имеет прежнего TTL-дедлайна, пока история удаления сохранена.
- Миграции SQLite аддитивные: persistent version counter, полные repair metadata, revision и consumer epoch. Старые repair без metadata при 404 источника сохраняются как нерешённые; уже потерянные до обновления данные или tombstones автоматически восстановить невозможно.
- Каждая перезагрузка ноды вызывает повторное чтение её текущего metadata stream соседями. Это плата за корректность cursor после backup restore. Байты одинаковых файлов повторно не скачиваются.
- Сохраняйте `meta_dir` и весь `sync_dir`, включая `.birak/storage-id`, в согласованном backup. При storage fault сначала восстановите ожидаемый том; удаление marker не является ремонтом. Sentinel контролирует root, а не независимые вложенные mount points.
- Используйте `/readyz` для допуска клиентского трафика и отдельно контролируйте peer health/lag/repairs. Readiness локального scan не подтверждает сходимость всего кластера. Длительный открытый SFTP writer может временно сделать scan неготовым.
- Checksum scan читает весь объём. Индексирование одного файла и локальный WebDAV COPY удерживают общий commit lock во время локального I/O; это нужно учитывать при больших файлах и деревьях. Отдельный редкий scrub и общий I/O budget не добавлены.
- Все ноды должны получить исправления: старый peer всё ещё может забывать удаления и применять прежние конфликтные правила. Совместимость wire-формата не означает полноту гарантий в смешанном кластере.

## Границы результата

Репликация остаётся eventual-consistent, с порядком по mtime и hash. Нет quorum, версии-конфликты не сохраняются обе, clock skew влияет на победителя. Прямые внешние filesystem writers не участвуют во внутреннем mutex: они должны публиковать файлы атомарно и не конкурировать за то же имя с gateway/репликацией. Permissions-only updates, пустые каталоги и конфликты файл/каталог не входят в контракт репликации файлов; COPY/MOVE дерева не являются crash-atomic транзакциями.

SIGKILL не отключает питание и не очищает файловый cache ОС. Hard crash VM/storage, реальные ENOSPC/EIO, длительная двусторонняя partition, миллионы файлов, большие объекты и целевые p95/p99 времени сходимости в этой проверке не измерялись. FULL и fsync реализуют порядок долговечности при корректной работе storage; испытание конкретного диска и длительный нагрузочный прогон остаются частью допуска целевого развёртывания к production.

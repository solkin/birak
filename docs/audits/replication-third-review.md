# Репликация: третья проверка и исправления

Исторический отчёт. Описанная ниже граница `a` / `a/child` устранена в [следующей доработке](replication-namespace-conflicts.md).

Дата: 2026-09-20. Предыдущая серия исправлений зафиксирована коммитом `638edd3` (`Harden replication commits, recovery, and integrity checks`). Эта проверка продолжает работу поверх него, без deployment.

Для удаления, доверия источникам, alias guard, directory alias indexing, recovery tombstone, рекурсивного COPY, overwrite race и отрицательных дат сначала получены падающие воспроизведения. Исправления проверяются обычными тестами без специальных build tags. Полный набор сохраняет предыдущие проверки process SIGKILL/restart, SFTP disconnect, offline/reconnect, ABA repair queue и protocol compatibility.

## Что стало проще

- Один `CommitFrom` проверяет storage, источники, затем выполняет общий протокол intent → filesystem → metadata. Обычный `Commit` использует тот же путь без источников.
- Один resolver используется для физического root, writer reservations, мутаций через directory aliases и защиты от рекурсивного COPY/MOVE.
- Удаление реплики больше не содержит отдельный алгоритм поиска и fsync surviving parent.
- Предусловия WebDAV повторяются под тем же lock, который защищает replacement.

## Оставшаяся граница

Пер-файловое LWW не определяет победителя между независимо созданными живыми `a` и `a/child` на разных нодах. Тест `TestConcurrentFileDirectoryConflictPreservesDataAndStaysVisible` подтверждает сохранность обеих сторон и видимую незавершённую repair queue, включая повторную попытку. Автоматической сходимости этого структурного конфликта сейчас нет. Нельзя исправлять его бездумным удалением дерева: это может уничтожить единственную копию данных. Для автоматического разрешения нужна отдельная согласованная политика конфликтов пространства имён.

`/readyz` по-прежнему проверяет локальное хранилище и scan; очередь repair и peers контролируются через `/status`. Асинхронный ACK, ограничения внешних writers и стоимость полных checksum scans остаются прежними. Проверка не моделирует отключение питания и не доказывает абсолютную безотказность.

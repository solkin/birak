# Доработка репликации после повторного аудита

Дата: 2026-09-20. Рабочее дерево поверх `e454e389234d2cd5a8bb859e60d20a6185aeb6d9`. Предыдущие изменения сохранены. Это реализация и локальная проверка, без deployment.

## Исправленные причины сбоев

| Проблема | Изменение | Проверка |
| --- | --- | --- |
| R01: потеря SFTP-записи через alias | Отдельный staging-файл до CLOSE; abort при разрыве сессии; защита имени, разрешённого symlink и исходного inode, включая hardlink; отказ второму writer | Оригинальное воспроизведение; alias/hardlink; rename/remove родителя; внешний replace; append; abort/create/overwrite; повторный CLOSE |
| R02: откат COPY/MOVE из-за старого mtime | Логический clock на каждое имя, независимый от mtime. Gateway индексирует старое состояние, сохраняет intent и индексирует результат до ACK. Replica сохраняет входящий clock | COPY/MOVE старого файла поверх нового; transitive relay через третью ноду; rollback mtime; delete/recreate; переходы файл ↔ каталог через HTTP peer |
| R03: удаление единственной копии после прерывания | Журнал replacement до переноса destination в backup. Startup восстанавливает незавершённую операцию до scan/sweep. Завершённые операции только очищаются. Неизвестный старый backup останавливает индексацию | 40 настоящих SIGKILL: COPY/MOVE × file/directory × destination exists/absent × 5 границ commit; повторное recovery; исходное воспроизведение; legacy backup |
| R04: ACK на подменённом томе | Проверка storage binding в общем пути gateway mutations, OPEN writer и CLOSE; повторная проверка при commit | Исходный WebDAV PUT на подменённый root; недоступная metadata DB не допускает удаления файла |
| R05: ABA в repair queue | Глобальная последовательность поколений в SQLite, сохраняемая после DELETE и restart; resolve и defer сверяют поколение. Дубликаты peers запрещены конфигурацией и удаляются защитно в Syncer.New; нормализованные URL также используются при очистке persistent queues | Старый worker после повторной вставки; сохранение очереди и поколения после restart; duplicate peer |
| R06: распространение незаметного повреждения | Необъяснимый hash mismatch с прежними size/mtime сохраняет проверенную метадату и запускает repair. Явная gateway mutation разрешена persistent intent | Исходная порча одного байта не распространяется; повреждение на initial scan восстанавливается с реального HTTP peer, repair queue очищается, readiness возвращается |

Дополнительно: persistent replica intent закрывает промежуток между публикацией файла и записью его метадаты; janitor сохраняет активные scratch-файлы даже со старым mtime; ОС не допускает второй daemon для того же тома/metadata directory и снимает lease после SIGKILL.

Все прежние `TestReview*` теперь выполняются без `syncrecheck`. Изменено одно прежнее ожидание: прямое переписывание байтов с сохранением size/mtime теперь проверяет quarantine, а не автоматическое объявление изменённых байтов правильной версией.

## Контракт

- ACK gateway означает локально опубликованный и проиндексированный результат. SFTP публикует на CLOSE; разрыв до CLOSE оставляет прежнюю версию.
- Перезапуск повторяет незавершённую индексацию из SQLite intents. Реплицированная запись сохраняет исходный conflict clock.
- Метаданные файла содержат три разных величины: `mod_time` для атрибута файла, `clock` для разрешения конфликтов, `version` для локального change stream.
- Прямые внешние изменения должны публиковаться атомарно и менять mtime. Для намеренного сохранения размера и mtime используется gateway. Если исправной реплики нет, quarantine остаётся видимым, данные не объявляются исправными автоматически.
- Все ноды обновляются вместе: протокол 2 отказывает старым/неизвестным версиям. Иначе старый peer мог бы отменить результат нового сравнения clock.
- Согласованность остаётся асинхронной, без quorum ACK и атомарной транзакции дерева между нодами. Конкурирующие независимые записи разрешаются детерминированно, обе версии не сохраняются.
- Полные checksum scans и локальное копирование держат общий commit mutex во время части I/O. Их пропускную способность нужно измерять на целевом объёме и диске; функциональные проверки не являются SLA.
- Питание, ядро и потеря filesystem cache не моделировались. SIGKILL означает прекращение пользовательского процесса.

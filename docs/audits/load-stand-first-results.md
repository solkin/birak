# Нагрузочный стенд: первые результаты

Дата: 2026-09-20. База: ветка `sync-production-readiness`, коммит `1b67613`.
Стенд: `bench_test.go`, запуск описан в README («Load stand»).

## Зачем

Все предыдущие проверки отвечали на вопрос «правильно ли». Стенд отвечает на
те, которые и решают допуск к production и которые функциональными тестами не
закрываются: сколько стоит запись, пока нода проверяет саму себя, за сколько
peer догоняет после отказа, и остаётся ли нода при этом ready.

Три фазы: заполнение и первичная индексация; непрерывная запись в одну ноду,
пока идёт скраб и реплицирует сосед; отказ соседа, запись в его отсутствие,
возврат и замер сходимости. Сходимость проверяется по **отпечатку манифеста**
(имя, хеш, состояние, clock, размер), а не по числу файлов: отказ, в котором
переписывались существующие имена, число файлов не меняет.

Отчёт начинается со **стоимости публикации на этой файловой системе** — голый
цикл «write, fsync, rename, fsync каталога». Без этой калибровки задержка
записи не интерпретируема: непонятно, это цена Birak или цена диска.

## Результат на macOS arm64 / APFS / NVMe

Конфигурация: 200 файлов по 16 KiB, один файл 16 MiB, 10 секунд записи,
скраб 4 MiB/с.

| Показатель | Значение |
| --- | --- |
| Стоимость публикации на ФС | **9.7 мс** |
| Задержка записи Birak, 1 писатель | p50 **45.8 мс**, p95 67 мс, p99 79 мс |
| Задержка записи Birak, 4 писателя | p50 **160 мс**, p95 207 мс, p99 225 мс |
| Пропускная способность записи | **~25 операций/с** — одинаково при 1 и при 4 писателях |
| Ожидание общего commit lock, 1 писатель | p50 24 мс |
| Первичная индексация | ~160 файлов/с |
| Сходимость после возврата ноды | 2.4–3.6 с на ~350 файлов |
| Отказы readiness под нагрузкой | **0** |

## Что из этого следует

**1. Запись сериализована полностью.** Пропускная способность не меняется при
росте числа писателей с 1 до 4, а задержка растёт линейно (45.8 мс → 160 мс,
ровно в четыре раза). Это подпись одной глобальной блокировки: конкуренция не
добавляет пропускной способности, она добавляет очередь.

**2. Скраб здесь ни при чём.** Прогон с `BIRAK_BENCH_SCRUB=0` даёт те же
25 операций/с и ту же задержку. Бюджетный скраб свою работу делает — он не
мешает записи.

**3. Запись стоит примерно в 4.7 раза дороже минимума этой ФС** (45.8 мс против
9.7 мс). Разница — в том, что commit индексирует имя **дважды**: `Begin`
наблюдает старое поколение до перезаписи, `Finish` индексирует результат.
Каждый проход — хеш, `fsync` файла, `fsync` родительского каталога и
транзакция SQLite с `synchronous=FULL`. Получается порядка шести fsync там, где
безопасная публикация требует двух. При измеренных ~5.9 мс на fsync это
объясняет наблюдаемые 45 мс почти полностью.

**4. Уровень 2 закрыл только половину.** Хеширование вынесено из-под общей
блокировки для *скана*. Путь commit по-прежнему хеширует под ней, причём
дважды, и для перезаписи большого файла `Begin` читает всё старое содержимое
до того, как запись вообще будет принята. На гигабайтном файле это тот самый
stall, который считался устранённым.

## Что сделано по этим выводам

Три правки, все на пути commit, ни одна не меняет гарантий.

**Индексация больше не fsync-ает то, что commit уже сделал долговечным.**
Проверено, что это верно для всех путей публикации: `closeWriter`, `Publish`,
`Rename`, `Remove`, WebDAV COPY через `copyFile` и MOVE через `ReplaceLocked` —
каждый fsync-ает байты до rename. Повторный fsync в `refreshFileLocked` остался
только для внешнего писателя, который мог не синхронизировать ничего.

**Staged-байты синхронизируются и хешируются до взятия блокировки.**
Временный файл принадлежит одному писателю, менять его некому, а rename
сохраняет inode — значит, снятые с него stat и хеш описывают опубликованный
файл точно. Результат передаётся индексатору через `fileops.Published`, и
`inspectFile` принимает его, пока поколение совпадает.

**`Begin` не перечитывает старое поколение, если stat не изменился.** Та же
логика, что уже работает в дешёвом обходе: совпали размер и время — читать
нечего. Подмена с сохранением обоих остаётся работой скраба.

Вместо трёх булевых параметров у индексации появился один `indexOptions` —
«что вызывающий уже гарантирует». Обещания в нём может дать только commit;
по умолчанию индексация по-прежнему никому не верит.

## Результат правок

Конфигурация **другая, чем в первой таблице**, и её числа с ней не сравниваются:
к стенду добавлен отдельный писатель, непрерывно перезаписывающий файлы по
32 MiB, — иначе цена работы под общей блокировкой ничем не создаётся. 200 файлов
по 16 KiB, два файла по 32 MiB, 15 секунд, один писатель мелких файлов,
скраб 4 MiB/с. Оба прогона — на одном диске, подряд.

| Показатель | До | После |
| --- | --- | --- |
| Задержка записи p50 | 73.8 мс | **46.0 мс** |
| Задержка записи p95 | 135 мс | **83.7 мс** |
| Ожидание общего commit lock p50 | 55.6 мс | **27.5 мс** |
| Пропускная способность | 13 оп/с | **20 оп/с** |
| Перезапись файла 32 MiB p50 | 117.9 мс | 125.1 мс |

Задержка самой большой записи не изменилась — и не должна была. Работа никуда
не делась, она вынесена из-под общей блокировки: fsync и хеш 32 MiB по-прежнему
входят в её собственную задержку. Выигрыш достался всем остальным, и видно его
в ожидании блокировки: оно упало вдвое, а обычная запись — на 38%.

Чтобы убрать и этот проход, писателю пришлось бы хешировать поток по мере
записи. `OpenWriter` отдаёт наружу `*os.File`, которым SFTP пользуется через
`WriteAt`, так что обёртка-хешер туда не встаёт без отдельной переработки
интерфейса.

Осталось три транзакции SQLite с `synchronous=FULL` на запись: `BeginLocal`,
`PutLocal` и `EndLocal`. Это и есть основная оставшаяся разница с 9.8 мс
минимума. `EndLocal` долговечности не требует — потерянное при отказе намерение
лишь заставит переиндексировать имя при старте, — но менять `synchronous`
поштучно означает отдельное соединение и отдельный набор проверок.

## Поправка: вывод про SQLite был неверным

Написанное выше — «запись стоит в 4.7 раза дороже минимума ФС, и основная
оставшаяся статья это три транзакции `synchronous=FULL`» — **не подтвердилось
измерением**. Замер по частям на том же диске:

| Операция | Время |
| --- | --- |
| `store.BeginLocal` | 72 мкс |
| `store.PutLocal` | 184 мкс |
| `store.EndLocal` | 73 мкс |
| `store.GetFile` / `HasLocalIntent` | 12 / 6 мкс |
| `watcher.checkStorageLocked` | 41 мкс |
| `os.Create` + запись 16 KiB + `Sync` | **4.7 мс** |
| Полная запись через `fileops`, ничего параллельно | **11.7 мс** |

Все три транзакции вместе — **0.33 мс**, меньше процента записи. Дорого стоит
fsync файла, а не метаданных.

Ошибка была в самом стенде: «стоимость публикации на ФС» он мерил в тишине, а
задержку записи — под нагрузкой. Сравнивать их напрямую нельзя, а отчёт именно
к этому и подталкивал. Теперь в отчёте три строки, и между ними видно, что есть
что:

```
publish floor        11.3 мс   цена файловой системы
write, node idle     14.2 мс   + собственные издержки Birak (~3 мс, 26%)
write, under load    60.0 мс   + очередь на единственной блокировке тома
```

Собственные издержки Birak на запись — около 26% поверх файловой системы, а не
4.7 раза. Всё остальное, что видно под нагрузкой, — **ожидание в очереди**, и
единственный способ это изменить — перестать сериализовать записи одной
блокировкой на том.

## Другие хрупкие места, найденные при этом разборе

**Скан держал в памяти имя каждого файла.** Проход удалений сравнивал индекс с
множеством всех имён на диске. На дереве в десять миллионов файлов это больше
гигабайта, который выделяет фоновая задача, — отказ ровно в тот момент, когда
нода занята. Множество убрано: проход удалений идёт по индексу постранично и
проверяет каждое имя одним `stat`. Памяти — страница, работы — вдвое больше
дешёвых `stat`, что для обхода приемлемо.

**`Store.AllFiles` загружал всю таблицу в память.** Помечен Deprecated, в
рабочем коде не использовался, но оставался готовой к вызову ловушкой. Удалён;
тест переписан на постраничный `ListNonDeleted`.

**Открытие файла без усечения копировало его целиком под общей блокировкой.**
Худший из оставшихся stall: SFTP-клиент, открывающий гигабайтный файл на дозапись,
останавливал все записи на ноде на время копии. Копия вынесена из-под
блокировки — писатель регистрируется до её снятия, поэтому назначение уже
занято для всех остальных commit, а внешнюю подмену по-прежнему ловит проверка
поколения при публикации. `TestSeedingDoesNotHoldTheCommitLock`: до правки
блокировка была доступна **0 раз** за копирование 64 MiB, после — десятки.

## Куда смотреть дальше

- **Сериализация записи** — теперь это единственная крупная статья. Пропускная
  способность не растёт с числом писателей: одна блокировка на том. Разделение
  по поддеревьям — большая и опасная работа; браться за неё имеет смысл только
  с числами этого стенда на целевом железе.
- **Хешировать поток по мере записи**, чтобы большая запись не читала свои же
  байты второй раз. Упирается в то, что `OpenWriter` отдаёт голый `*os.File`.
- **`synchronous=FULL` на macOS не равен долговечности при отказе питания**:
  Go вызывает `fsync`, а APFS сбрасывает кеш диска только по `F_FULLFSYNC`.
  Числа выше сняты на macOS; на Linux соотношение сохранится, абсолютные
  значения — нет. Проверять надо на целевой ФС.

## Как это проверено

`go vet ./...` и `go test -race -count=1 ./...` — зелёные. Корневой пакет
дополнительно прогнан 6 раз подряд без `-race` и 4 раза с ним: один отказ,
случившийся сразу после правки, больше не воспроизвёлся ни разу за 13 прогонов,
и его текст не был сохранён — считать его объяснённым нельзя. Четыре новых теста в
`internal/watcher/commit_indexing_test.go` закрепляют механику: commit
использует уже прочитанные байты (доказывается хешем-часовым), подсказка от
другого поколения отбрасывается, реальная запись через `OpenWriter`
индексируется тем, что лежит на диске, а поколение, которого индекс никогда не
видел, по-прежнему читается целиком.

Утверждение «каждый путь публикации fsync-ает байты до rename» проверено
чтением кода, а не тестом: `closeWriter`, `Publish`, `Rename`, `Remove`,
`copyFile` в WebDAV COPY и `ReplaceLocked` в MOVE. Отказ питания в unit-тесте
не воспроизводится, поэтому это остаётся утверждением ревью — и требованием к
любому новому пути публикации.

Побочный эффект переноса fsync из-под блокировки: если commit потом
отказывается (destination изменился под нами), прочитанные и захешированные
байты пропадают зря. Это редкий случай — требуется конкурентная внешняя
подмена, — и он стоит дешевле, чем удержание блокировки на каждой записи.

## Замечено, но не исправлено

- **Сверка проходит весь манифест каждого peer раз в час.** На десяти миллионах
  имён это десять тысяч запросов в час на peer и столько же пакетных обращений
  к индексу. Для целевых трёх нод это вопрос объёма данных, а не кода.
- **`/status` и `/metrics` считают очередь полным проходом** (`COUNT`, `SUM`,
  `MIN` без индекса по `first_seen`). При очереди в сто тысяч строк и опросе
  раз в 15 секунд это приемлемо, при большем — стоит кешировать на секунду.
- **`log_level: debug` по-прежнему пишет синхронно из горячего пути.** Уровень
  по умолчанию `info` это снимает, но при включённом debug залипший сборщик
  логов по-прежнему тормозит ноду.
- **Один отказ корневого пакета**, случившийся сразу после перехода на единый
  путь применения, не воспроизвёлся ни разу за 13 последующих прогонов, и его
  текст не сохранён. Объяснённым считать нельзя.

## Чего стенд не измеряет

Протокольные издержки (S3/WebDAV/SFTP поверх HTTP), поведение на сетевом томе,
отказ питания, восстановление из backup, и сходимость на канале с реальной
задержкой. Передача, которая продолжает двигаться, общего дедлайна не имеет, —
ни одно число отсюда не ограничивает отставание репликации на медленной линии.

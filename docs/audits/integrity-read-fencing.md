# Целостность чтения и восстановление после отказов

Дата: 2026-10-07. Первый этап доработок после проверки production-контура.

Карантин теперь хранится в SQLite и загружается при открытии store. Ремонт
равного состояния после перезапуска больше не пропускается как уже выполненный.
Все пять путей чтения — S3, WebDAV, SFTP, HTTP UI и peer API — используют один
контролируемый reader. Обнаружение порчи отзывает открытые дескрипторы, включая
алиасы. После замены файла дескриптор старого повреждённого inode остаётся
заблокированным. Долговечный реестр повреждённых поколений также запрещает
повторное открытие hard link к вытесненному inode после рестарта.

Операции чтения держат только собственную блокировку дескриптора, ограничивая
размер одного чтения 64 КиБ. Сетевой вывод не удерживает блокировку тома.
Карантин не может отозвать уже доставленные клиенту байты. Период до обнаружения
порчи всё ещё определяется проверкой контрольных сумм. Записи повреждённых
поколений сохраняются консервативно; автоматического GC по возрасту нет.

Recovery replica intent повторяет fsync файла и surviving parent до фиксации
индекса и очистки intent. Снятие карантина после удаления тоже требует fsync
каталога. Ошибки сохранения/снятия карантина возвращаются вызывающему коду;
ошибка записи карантина дополнительно сохраняет запрет чтения в памяти.

Оба HTTP-клиента репликации отказываются следовать редиректам, включая переход
на другой адрес того же хоста. Общий секрет не покидает сконфигурированный peer.

DeleteBucket больше не удаляет ignored-файлы. Одинаковый контрактный тест
добавлен в Birak и Sebastian. Платформенные identity, lease и directory-sync
helper перенесены из Sebastian; Birak снова собирается под Windows. В обоих
проектах добавлен Windows build job. Directory fsync на Windows остаётся
best effort; сборка не доказывает power-loss durability на NTFS.

## Проверки

| Проверка | Результат |
| --- | --- |
| Исходные воспроизведения до изменения | Падающие тесты: quarantine read, restart, SFTP, redirect, clock overflow |
| Полный macOS arm64 набор с race detector | 701 PASS, 2 SKIP, 0 FAIL |
| Полный Linux arm64 набор с race detector, непривилегированный UID | 702 PASS, 2 SKIP, 0 FAIL |
| Настоящий ENOSPC в Linux | PASS для data, data mid-transfer и metadata |
| Полный набор Sebastian с race detector | PASS |
| Повтор на трёх процессах | Partition, SIGKILL и испорченные передачи сходятся; quarantined reads теперь возвращают ошибку без повреждённых байтов; последующий repair восстанавливает чтение |
| Linux strace recovery | fsync data/file, затем fsync data directory, затем fsync SQLite WAL |
| Windows amd64 cross-build и go vet | PASS |

После ревью дополнительно проверены сохранение запрета для displaced inode,
ошибки SQLite при сохранении/снятии карантина, GET/Range всех HTTP gateway,
существующие SSH/SFTP-сценарии и очистка quarantine при долговечном удалении.
Гонка ожидания в `TestIntegration_PartialDirCleanup` исправлена ожиданием
конечного состояния каталога.

## Следующий этап

Асинхронный ACK и LWW в этом этапе не меняются. Новая пустая нода всё ещё не
получает автоматический допуск в балансировщик по факту завершения bootstrap;
restore с новым mtime, граница часов `MaxInt64-1` и несовместимость регистра имён
тоже требуют следующего этапа. Простое понижение максимально принимаемого clock
переносит отказ на репликацию следующей локальной записи, поэтому такая поправка
не включена. Power-cut и native NTFS не проверены. Текущий этап не означает готовности
к заявленной гарантии сохранности подтверждённой записи при потере ноды.

Принятый контракт следующего этапа описан в [модели кворума](../quorum-design.md).

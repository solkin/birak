# Готовность filesystem-репликации к production

Состояние на 2026-10-08. Подробности изменений и воспроизводимые проверки — в
[отчёте приёмки](audits/filesystem-production-hardening.md) и
[отчёте APK/иконок](audits/apk-read-production-load.md).

## Оценка

Filesystem остаётся автономной асинхронной репликацией: доступность локальной
записи не зависит от лидера, большинства или списка живых соседей. Разделения
сети, возврат старой согласованной копии и подключение новой реплики проверены
на настоящих процессах в локальных Linux Docker-контейнерах. Найденные отказы
с потерей данных при коллизиях имён, повышением ранга старых файлов и
исчерпанием clock исправлены и покрыты регрессиями.

Это основание для ограниченного production на проверенном Linux-хранилище с
измеренной нагрузкой, резервным копированием и мониторингом. Локальный TLS
профиль APK/иконок превысил среднюю цель 10 TB/сутки примерно вдвое. Приёмка
суточной нагрузки на целевых дисках и внешнем uplink, нативного NTFS и
физического отказа питания остаётся отдельной работой.

## Что проверено

| Поведение | Подтверждение |
| --- | --- |
| Локальные ACK и чтение при изоляции ноды | Docker-стенд: запись на обеих сторонах разделения |
| Сходимость после возврата сети | Полные manifest и очереди; независимые SHA256 чтения живых объектов |
| Старый backup с потерянными mtime не отменяет новое удаление/overwrite | Docker-стенд и `backup_test.go` |
| Новая реплика не попадает в балансировщик до начального применения данных | `/readyz`; отрицательный admission marker переживает частичную загрузку и рестарт |
| Уход соседей не отзывает уже полученный admission | Проверка изоляции и сохранения marker после рестарта |
| Case/Unicode-коллизия не перетирает другой объект | Регрессии store/syncer, APFS и S3 PUT в Docker |
| Clock выше int64 сохраняется и допускает следующие локальные записи | Store migration/reopen, namespace ordering и реальная HTTP-репликация |
| Повреждение с прежними размером и mtime обнаруживается и восстанавливается | Карантин/read fencing в тестах; scrub и repair на Docker-стенде |
| Индекс и подтверждённые записи восстанавливаются после SIGKILL | Реальные daemon fault-тесты в полном Linux/macOS наборе и Docker-стенд |
| Переполнение диска не публикует неподтверждённый индекс | Linux race-набор с отдельным tmpfs 16 MiB |
| LIST работает после первых 100000 объектов | 500000 физических иконок, последние 1000 ключей получены через S3 |
| Частое чтение APK и иконок не блокируется хешированием watcher events | Проверяемый TLS, 10/100/500 MiB, concurrent uploads/events, 1000 offered icon GET/s |
| Backup незавершённой replica publication с потерянным mtime сохраняет версию | Детерминированный regression с новым файлом/overwrite и реальный restore |
| Зависимости без известных достижимых уязвимостей | `govulncheck` Linux/macOS и Windows-target; проверка добавлена в CI |

Полные `go test -race -count=1 -timeout 900s ./...` прошли на macOS/APFS и
Linux/Go 1.26 под UID 1000. Пропущены опциональные benchmark/scale и helper
дочернего процесса; million-name scale проверен отдельно. Проверены
`go vet`, сборки Linux/Windows и Docker-образ. Сборка Windows не заменяет
исполнение на NTFS.

## Измеренная нагрузка

Локальный Docker Desktop: Linux arm64, 8 CPU, около 14.6 GiB RAM, отдельные
Docker data/meta volumes. Профиль: 500000 отдельных физических иконок,
семь synthetic APK payloads 10–500 MiB, verified TLS и signed SigV4. Все
полные передачи проверяются SHA256; conditional GET проверяет 304/ETag.
Иконки хранятся готовыми: извлечение из APK не входит в этот тест.

При offered APK rate 240 MiB/s и icons 1000/s измерены **220.71 MiB/s APK**
с учётом завершения больших передач — около **20 TB/сутки** при непрерывной
такой скорости. За активные 60 секунд обработано 59507 icon requests,
около 992/с; с 15 секундами drain — 793/с. Icon TTFB p99 **4.854 ms**,
worst **209.2 ms**. Ошибок bytes/hash/transport нет, одновременно прошли
6 uploads и watcher events для 500 MiB файла; scrub включён.

Рабочий набор помещается в RAM. Это короткий warm-cache прогон внутри Linux
bridge, а не переданные 20 TB, холодное I/O или внешний production uplink.
Go client через macOS published ports дал только 7.3–7.6 TB/day APK с icons;
такой путь порог не прошёл. Максимальный Linux bridge прогон дал около
2 GiB/s APK, но icon p99 вырос до 107 ms. Внешние пики требуют отдельной
приёмки, а не экстраполяции этих цифр.

Startup sweep на 500007 физических файлах сократился с 22.39 до 5.18 секунды.
S3 LIST последних 1000 иконок: прежде неполный пустой результат за 477 ms,
теперь полный за 27.2 ms. Миллион metadata names: глубокая страница 1000
записей за 2.12 ms. Fixture уже индексирован; первоначальное чтение 5–250 TB
APK не измерялось.

Четырёхнодовый fault-прогон с объектом **500 MiB**: 1000 исходных объектов,
12 конкурентных писателей 20 секунд, 2861 успешных PUT. Сходимость после
соединения сети — 39.34 секунды, 3286 живых объектов проверены независимо.
S3 stress PUT p50/p99 — 43.7/337.3 ms.

Проверены частичная загрузка новой ноды с SIGKILL/restart, реальное восстановление
старых data/meta с потерянными mtime и повреждение bytes с прежними размером и
точным mtime. Ноды сошлись, удаление/overwrite сохранились, повреждённый файл
карантинирован и восстановлен. Полное время — 274.68 секунды. Memory snapshot
в конце: 25–51 MiB на daemon; это снимок, а не доказательство отсутствия утечек.

После исправления окна recovery replica intent финальный повтор на
пересобранном образе тоже прошёл все проверки: 1728 PUT, 2380 проверенных
объектов, сходимость 47.06 s. Он шёл параллельно с race-наборами и используется
для проверки корректности; performance сравнивается по отдельным прогонам.

Первый более длинный сетевой прогон дал 2922 PUT за 45 секунд и 3336 проверенных
живых объектов. Его restore step исключён: вложенные Docker VOLUME скрывали
parent mount от helper-контейнеров. Исправленный стенд явно монтирует sync/meta
и проверяет наличие старых bytes и SQLite до/после offline restore. Обе ошибки
инъекции стенда и их исправления сохранены в отчёте приёмки. Цифры этого стенда
не устанавливают production SLA.

Отдельный Linux benchmark на Docker-volume (1000 × 64 KiB + 2 × 32 MiB,
12 writers, 20 секунд) прошёл: 2669 записей, 133/с; p50/p99 под нагрузкой
80.5/215.9 мс, idle p50 4.35 мс; среднее удержание commit lock 2.25 мс.
Первичная индексация 1002 файлов — 1.85 секунды; сходимость после возврата
соседа — 9.75 секунды, readiness failures — 0. Это компонентный benchmark,
а не измерение S3 по сети.

Commit на одном томе по-прежнему сериализован. Долговечный rename/fsync и
SQLite commit ограничивают throughput; добавление писателей не устраняет
ограничение. Измерять на целевом хранилище и распределении размеров файлов:

```sh
BIRAK_BENCH_DIR=/path/to/disposable/test-volume go test -run TestBenchSyncUnderLoad -v -timeout 30m .
```

## Границы выбранной стратегии

- ACK означает долговечную локальную публикацию. Потеря единственной ноды до
  передачи соседям может потерять подтверждённую запись. Исчезновение всех
  физических копий данных не восстанавливается автоматически.
- Одновременные изменения одного имени разрешаются детерминированным порядком;
  все конкурирующие версии обычного файла не сохраняются. Начальные часы могут
  влиять на выбор победителя.
- Tombstones и резервирование написания имён хранятся бессрочно, чтобы произвольно
  старая нода могла вернуться. SQLite и manifest растут с историей разных имён.
- `App.apk` и `app.apk`, включая каталоги и Unicode-эквивалентные написания,
  не могут сосуществовать. Независимые коллизии требуют изменения имён оператором;
  данные сохраняются, repair остаётся видимым. Case-only rename не поддерживается.
- Backup должен согласованно включать данные, metadata и `.birak/storage-id`.
  Потерянный mtime исправляется для неизменённых байтов с индексом или durable
  replica intent. Без соответствующих metadata или при других байтах старый файл неотличим от нового
  пользовательского ввода. Копировать после остановки процесса.
- `/readyz` допускает новую пустую реплику после сравнения и применения состояния
  хотя бы одного источника; это не доказательство глобальной свежести. Балансировщик
  должен соблюдать readiness; сами gateways доступны во время загрузки.
- На Windows fsync каталогов остаётся best effort. SIGKILL сохраняет page cache
  и проверяет восстановление процесса, но не потерю питания.

## Что нужно для целевого deployment

1. Длительный soak на целевых дисках и uplink, с cold-cache I/O, пиковым
   throughput и фактической частотой скачивания иконок.
2. Проверка power loss на управляемой VM/оборудовании и нативная NTFS-проверка,
   если Windows входит в deployment.
3. Восстановление согласованной копии вашим backup-инструментом.
4. Scrub budget под требуемый срок обнаружения: 10 TB при 8 MiB/s — примерно
   14 дней на один цикл без учёта конкуренции за I/O. `0` отключает scrub.
5. Все реплики обновляются до protocol 4; Go 1.26 или новее для сборки.
   Сохранить pre-upgrade metadata для отката. Legacy aliases могут остановить
   миграцию с явной ошибкой; разрешить их до запуска новой версии.

## Мониторинг

Следить за `birak_peer_healthy`, `birak_repair_oldest_seconds`,
`birak_quarantined_files`, `birak_last_scan_seconds`,
`birak_last_scrub_seconds`, `birak_skipped_entries_total`.
`birak_replica_initialized` показывает admission новой реплики,
`birak_scrub_bytes_per_second` — заданный бюджет,
`birak_directory_sync_best_effort` — ослабленную гарантию fsync каталога.
Возраст завершённого scrub не является сертификатом целостности всех байтов.

`birak_active_readers`, `birak_file_read_bytes_total` и
`birak_reader_revocations_total` показывают чтение общих файловых дескрипторов
и отзыв повреждённых поколений. Bytes включает replication/probes; подтверждённый
egress и частоту icon requests измерять на ingress/proxy.

`rate(birak_commit_lock_held_seconds_total[5m])` около единицы указывает на
насыщение сериализованного commit. Возраст repair и backlog нужно оценивать
отдельно: автономная нода остаётся ready при недоступных соседях.

# Кворумная запись и изменение состава кластера

Статус: требования и целевой проект. Реализовано и проверено отдельное ядро
`internal/generation` + `internal/quorum`; в `birakd` и шлюзы оно пока не
подключено. Текущие гарантии и границы — в
[аудите ядра](audits/quorum-core.md).
Дата: 2026-10-07.

Birak должен работать на одной ноде и позволять добавлять ноды без остановки
кластера. Число три не является константой протокола. Успешная запись должна
означать долговечное сохранение данных и решения об их публикации на кворуме
текущего согласованного состава. Подтверждение чтения change stream, пустая
repair queue или наличие похожих метаданных не являются подтверждением данных.

## Состав и подтверждение

Для N голосующих нод кворум равен `floor(N/2)+1`: 1/1, 2/2, 2/3, 3/4, 3/5 и
далее. Один узел работает автономно, но не переживает безвозвратную потерю своего
единственного диска. Неголосующие реплики могут использоваться для удалённого
резервирования. Их наличие само по себе не меняет кворум.

При partition размер кворума не пересчитывается по доступным адресам.
Недостаточное число подтверждений означает отказ/неопределённый исход записи,
а не тихое переключение на локальный ACK. Изменение состава является отдельной
согласованной операцией. Изолированная нода не может объявить себя новым
одиночным кластером на основании отсутствия ответов.

Для управления порядком commit и membership выбран
[HashiCorp Raft](https://github.com/hashicorp/raft) 1.7.3;
правила безопасности смены состава и фиксации журнала описаны в
[публикации Raft](https://raft.github.io/raft.pdf). В журнале должны находиться
небольшие команды и ссылки на поколения файлов. APK в сотни мегабайт требуют
отдельной передачи: библиотека [предупреждает о больших log entries](https://github.com/hashicorp/raft/blob/main/api.go).

Кворум метаданных недостаточен: потеря ноды не должна оставлять согласованный
указатель на отсутствующие байты. Перед commit нужны проверенные долговечные
копии конкретного неизменяемого поколения на требуемых участниках. Поколение
нельзя удалить или перезаписать, пока оно необходимо для восстановления либо
исполнения уже принятого решения. Удаления также должны получать согласованное
подтверждение. Повтор операции определяется её устойчивым идентификатором;
таймаут клиента не означает гарантированный rollback.

## Присоединение и вывод

1. Первая нода создаёт новый cluster ID только явным bootstrap на новом
   состоянии. Повторный запуск восстанавливает существующий состав.
2. Новая нода присоединяется без голоса и без клиентского трафика. Она получает
   согласованный snapshot метаданных и все требуемые поколения, затем догоняет
   изменения после snapshot. Имя ноды уникально; кластер, протокол и политика
   пространства имён проверяются до приёма данных.
3. Завершение bootstrap подтверждается относительно commit boundary и
   фактического наличия файлов. Произвольный процент догнанного журнала или
   нулевая очередь не являются достаточным условием.
4. Повышение до голосующей ноды проходит через согласованное изменение состава.
   Переходы 1→2, 2→3 и N→N+1 используют один протокол. В каждый момент
   действуют определённые правила подтверждения, без независимых локальных
   представлений о числе голосов.
5. Перед выводом прекращается приём новых клиентских записей на ноде,
   обеспечиваются необходимые копии на остающихся участниках, фиксируется
   новый состав и отзывается доступ. Если достаточный состав недоступен,
   операция ждёт или возвращает ошибку; автоматического принудительного
   уменьшения кворума нет.
6. Восстановленная копия присоединяется в режиме догоняния. Её локальные
   timestamps не могут объявлять старые файлы новыми cluster commits.

## Граница с нынешней реализацией

Сейчас gateway изменяет файловую систему и индексирует результат под общим
commit lock. Ожидание peers внутри `Hooks.Finish` заблокирует peer-чтение этого
же файла. Ожидание после снятия lock без фиксации поколения позволит следующей
перезаписи заменить подтверждаемые байты. Поэтому сетевое ожидание необходимо
выделить из локальной публикации, а подтверждение связать с неизменяемым
поколением и согласованным решением.

Watcher не должен обходить протокол commit, превращая внешний filesystem diff
в самостоятельную подтверждённую версию. Для внешних writers и миграции старого
каталога нужен явный режим импорта. Для S3, SFTP и WebDAV требуется один путь
публикации, включая multipart completion, CLOSE, COPY/MOVE и удаления деревьев.
Согласованность чтений и история версий должны быть описаны до переключения
gateway: долговечность нескольких копий сама по себе не определяет, какую
версию увидит клиент при конкурентных операциях.

Физические имена файлов не могут служить единственным пространством S3-ключей
на смешанных файловых системах. Вариант представления ключей и поддержка
Windows должны исключать незаметное схлопывание разных логических имён.

## Приёмка

Матрица размеров кластера: 1, 2, 3, 4, 5 и произвольный больший N в модельных
тестах. Проверки: online join под записью, leader failover, minority partition,
restart во время изменения состава, повторы и таймауты, повторный join,
отключение единственного владельца поколения, старый backup, утрата метаданных,
ошибки fsync и переполнение data/meta/staging. Каждый успешный ACK должен
проверяться независимым чтением нужного поколения с оставшихся нод после
допустимых отказов. Подтверждённое изменение состава также проверяется после
перезапуска всех процессов.
